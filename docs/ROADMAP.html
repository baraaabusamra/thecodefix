The Code Fix — الخطة الكبرى الموحّدة

هذا هو المرجع الرسمي الوحيد للخطة المستقبلية للمشروع. يوثّق الوجهة، الأولويات، الميزات، خطة SEO، مؤشرات النجاح، وطريقة العمل. آخر تحديث: 2026-09-05.

ما هو مبني الآن موثّق في PROJECT.md، وقواعد المحتوى في content-guidelines.md، وقواعد SEO الإلزامية في seo-technical-policy.md. عند اختلاف وثيقة قديمة مع هذه الوثيقة في الأولوية أو التاريخ، تعتمد هذه الوثيقة.

1) الوجهة التي نريد الوصول إليها

الرؤية

أن يصبح The Code Fix المنصة العربية الأكثر فائدة وموثوقية لتعلّم البرمجة تطبيقيًا: يتعلّم المستخدم المفهوم، يجرّبه، يتدرّب عليه، ينجز مشروعًا، يختبر نفسه، يثبت مهارته، ثم ينتقل إلى فرصة تعليمية أو مهنية مناسبة.

لسنا بصدد بناء أكبر عدد من الصفحات. نريد بناء أفضل منظومة تعلّم عربية مترابطة:

بحث Google
  → إجابة دقيقة ومفيدة
  → مسار تعلّم واضح
  → درس وتطبيق عملي
  → تمرين أو مشروع
  → اختبار وشهادة
  → حساب وعودة أسبوعية
  → فرصة عمل أو خدمة مدفوعة ذات قيمة حقيقية

الوعد الأساسي

  • التعلّم الأساسي يبقى مجانيًا.
  • المحتوى العربي واضح، أصلي، دقيق، ومراجع.
  • كل صفحة لها غرض تعليمي أو عملي حقيقي، وليس غرضًا شكليًا لـSEO.
  • الميزات المدفوعة مستقبلًا تبيع قيمة إضافية، ولا تحجب أساسيات التعلّم.

الهدف خلال 12 شهرًا

  1. تثبيت نمو عضوي مستمر بدل الاعتماد على نشر صفحات كثيرة بلا قياس.
  2. تحويل الزيارة إلى رحلة تعلّم قابلة للقياس، وليس مجرد مشاهدة صفحة.
  3. إطلاق منظومة تمارين ومشاريع لأول المسارات ذات الطلب المثبت.
  4. بناء قناة عودة نملكها: حساب فعّال + بريد أسبوعي + مشاركة الشهادات.
  5. تفعيل أول مصدر دخل بعد إثبات الاستخدام والقيمة، لا قبله.
  6. تشغيل الموقع بمراقبة ونسخ احتياطي وأمان يناسب نموّه.

  • Next.js App Router مع صفحات عامة ثابتة وSSG على نطاق كبير.
  • 51 مسارًا تغطي أساسيات البرمجة والويب والأنظمة وCloud وAI والأمان.
  • محرر JavaScript وHTML وPython داخل المتصفح.
  • تقدّم مستخدم، اختبارات، شهادات قابلة للتحقق، وحساب متعلّم.
  • مدونة، مرجع، خرائط طريق، وظائف، تدريب، جامعات، ومنشئو محتوى.

  • canonical وsitemap وrobots وJSON-LD وقواعد SEO آلية داخل CI.
  • فحوص روابط، metadata، H1، صفحات يتيمة، مراجع، اختبارات ومحتوى أكاديمي.
  • بناء كامل ناجح لـ3,853 صفحة في آخر تحقق.

الفجوات الحالية

  1. القياس: حُفظ أول خط أساس فعلي لـSearch Console بتاريخ 2026-09-05؛ أرقام التحويلات تبقى بلا خط أساس إنتاجي حتى نشر الأحداث وجمع بيانات حقيقية.
  2. التحويل: المنصة غنية بالمحتوى، لكن رحلة "دخل → بدأ → أكمل → عاد" ليست مقاسة بالكامل بأحداث واضحة.
  3. التطبيق العملي: التمارين وبنك الأسئلة العميق ما زالا محدودين مقارنة بحجم 51 مسارًا.
  4. العودة: لا توجد بعد قناة بريدية ونظام عادات تعلّم متكامل.
  5. الربح: Stripe موجود برمجيًا لكن الدفع غير مفعّل في الإنتاج، ولا يجوز إطلاق Pro قبل بناء الاستحقاقات والقيمة والدعم.
  6. التشغيل: نحتاج خطة نسخ احتياطي موثقة، مراقبة أخطاء، rate limiting، ومراجعة CSP.
  7. الدين التقني: ترقية Next.js الأمنية تحتاج دفعة مستقلة، ونظام استخراج المناهج يجب ألا يصرف على عمليات تنتهي في queue لا يراجعها أحد.
  8. تباين الجودة: بعض المحتوى القديم، خصوصًا المقارنات القصيرة، يحتاج تحسينًا أو دمجًا قبل إنتاج مقارنات جديدة.

3) مبادئ القرار

أي عمل جديد يجب أن يحقق واحدًا على الأقل من الآتي:

  1. يجلب الزائر المناسب.
  2. يساعده على إكمال نتيجة تعليمية.
  3. يجعله يعود.
  4. يفتح دخلًا دون الإضرار بالثقة أو المجانية الأساسية.
  5. يقلل خطرًا حقيقيًا في الأمان أو التشغيل أو جودة المحتوى.

قواعد لا نتجاوزها

  • البيانات قبل التوسع: لا مسار أو قسم ضخم جديد بلا إشارة طلب أو فجوة تعليمية مثبتة.
  • Update/Merge قبل Create: نطبّق اختبار وجود الصفحة من content-guidelines.md قبل أي URL جديد.
  • مرحلة واحدة رئيسية في كل وقت: يمكن تنفيذ صيانة صغيرة بالتوازي، لكن لا نفتح مشروعَي منتج كبيرين معًا.
  • دفعات صغيرة قابلة للمراجعة: محتوى 5–8 صفحات في الدفعة، وكود بحدود واضحة.
  • لا نشر آلي لمحتوى حساس: الأمان، البيانات الجامعية، الوظائف، والادعاءات المتغيرة تحتاج المصادر والمراجعة المحددة في سياسات المشروع.
  • الصفحات العامة تبقى static متى أمكن: أي تغيير يجعلها dynamic يحتاج سببًا وقياسًا واضحين.
  • لا ضمانات ترتيب: SEO يزيد شروط النجاح، لكنه لا يضمن مركزًا محددًا.
  • لا تحديث تاريخ وهمي: dateModified يتغير فقط عند تعديل حقيقي مفيد.

4) ترتيب التنفيذ — الخريطة الزمنية

المرحلة 0 — تثبيت الأساس والقياس (الأيام 1–10)

الهدف: نعرف نقطة البداية بالأرقام، ونغلق المخاطر التي قد تعطل النمو.

0.1 خط أساس Search Console

الحالة في 2026-09-05: اكتملت القراءة الفعلية من حساب المالك ووُثقت في docs/seo-baseline-template.md: أداء 28 يومًا و3 أشهر، الفهرسة وأسباب الاستبعاد، sitemap، Crawl Stats، الدول والأجهزة، وأفضل الصفحات والاستعلامات، مع URL Inspection لعينة من القوالب. لم يُطلب indexing ولم تتغير إعدادات GSC. خط أساس التحويلات يبقى بعد نشر أحداث القياس وجمع نافذة بيانات إنتاجية.

  • تصدير آخر 28 يومًا وآخر 3 أشهر مع مقارنة بالفترة السابقة.
  • تسجيل: clicks، impressions، CTR، average position.
  • فصل branded عن non-branded متى كانت البيانات كافية.
  • تصنيف الأداء حسب: الصفحة، الاستعلام، الدولة، الجهاز، ونوع البحث.
  • تسجيل عدد الصفحات: indexed، not indexed، crawled-not-indexed، discovered-not-indexed.
  • فحص يدوي لعينة من كل قالب: الرئيسية، المسار، الدرس، المدونة، المرجع، الوظائف، الجامعات، ومنشئي المحتوى.
  • إنشاء قائمة "فرص سريعة": صفحات بمركز 5–20، أو impressions جيدة وCTR ضعيف.

0.3 إغلاق المخاطر التشغيلية ذات الأولوية

  • مراجعة وشحن إصلاح CTAs صفحة الأسعار الحالي كدفعة مستقلة.
  • ترقية Next.js والتبعيات الأمنية في فرع مستقل بعد قراءة وثائق النسخة، ثم CI كامل واختبار بصري للمسارات الحساسة.
  • تعطيل تشغيل extraction المدفوع افتراضيًا ما دام مسار المراجعة محذوفًا؛ لا نحذف queue أو بياناتها التاريخية.
  • توثيق نسخة احتياطية واستعادة تجريبية لقاعدة Neon والمحتوى.
  • إضافة مراقبة أخطاء production وتنبيه للأخطاء المتكررة.
  • وضع rate limiting على checkout، الاقتراحات، وأفعال الكتابة العامة.
  • بدء CSP بوضع Report-Only، ثم فرضها بعد مراقبة Playground وOAuth والتحليلات.

الحالة في 2026-09-05: تم محليًا إصلاح CTAs وتعطيل extraction المدفوع افتراضيًا. أُغلقت محليًا فجوات rate limiting لأفعال الكتابة العامة، وأضيفت مراقبة أخطاء آمنة مع error boundaries وتنبيه webhook اختياري، وبدأت CSP في وضع Report-Only مع collector محدود الحجم والمعدل. التفاصيل التشغيلية في docs/production-monitoring-runbook.md والتدقيق في docs/phase-0-security-hardening-audit.md. تفعيل التنبيه في الإنتاج يحتاج ضبط ERROR_ALERT_WEBHOOK_URL، وفرض CSP يبقى مؤجلًا إلى ما بعد نافذة مراقبة مدتها أسبوع إلى أسبوعين وقرار استراتيجية nonce/SRI/static. لم تُنشر التغييرات بعد. كما وُثقت إجراءات النسخ والاستعادة في docs/backup-restore-runbook.md؛ لا تُغلق بوابة النسخ الاحتياطي حتى ينفذ المالك restore drill على قاعدة معزولة ويسجل RPO/RTO الفعليين.

المرحلة 1 — SEO: تحسين الموجود قبل زيادة الصفحات (الأسابيع 2–6)

الهدف: جعل أقوى الصفحات الموجودة تستحق الفهرسة والنقر والعودة.

1.1 تقسيم المخزون

كل صفحة تدخل واحدة من أربع مجموعات:

المجموعة الوصف الإجراء
A impressions ومركز 5–20 تحسين سريع للنية والعنوان والروابط
B مفهرسة لكن CTR ضعيف تحسين title/description ووضوح الوعد
C غير مفهرسة لكنها ذات قيمة تقوية المحتوى والروابط والـpillar ثم طلب فحص محدود
D رقيقة أو مكررة أو بلا طلب تحسين أو دمج أو 301 أو إيقاف؛ لا تجميل شكلي

1.2 الصفحات المحورية

  • تدقيق صفحات المسارات الـ51، والبدء بأعلى 5 مسارات حسب GSC لا حسب الانطباع.
  • كل صفحة مسار توضّح: لمن المسار، ماذا سيتعلم، المتطلبات، المدة التقريبية، النتائج، الدروس، المشاريع، الاختبار، والخطوة التالية.
  • ربط المسار بالمقالات والمراجع والاختبار والخريطة المناسبة بروابط وصفية.
  • عدم حشر كل الروابط في الصفحة؛ نعرض ما يخدم قرار المتعلم فقط.

1.3 تحسين الثقة والجودة

  • مراجعة صفحات المقارنات القديمة والقصيرة قبل إنشاء مقارنات جديدة.
  • إظهار المؤلف أو الجهة المراجعة بطريقة صادقة حيث يتوقع القارئ ذلك.
  • توضيح منهجية المراجعة واستخدام AI عندما يكون هذا مفيدًا لفهم "كيف" أُنتج المحتوى.
  • تواريخ مراجعة حقيقية، مصادر رسمية للادعاءات المتغيرة، وأمثلة منفذة.
  • صور ولقطات ودياغرامات أصلية للصفحات المحورية والمفاهيم الصعبة.
  • جدول محتويات مناسب للجوال للمحتوى الطويل.
  • لا نكتب بطول مستهدف؛ الطول يتبع حاجة المستخدم.

1.4 الربط الداخلي

النموذج الأساسي:

Track → Lesson → Reference → Exercise/Project → Quiz → Roadmap

والنموذج الأكاديمي يبقى مستقلًا:

Country → University → Specialization → Study Plan/Course

لكل صفحة جديدة أو محسنة نراجع:

  • الرابط إلى الأب أو الصفحة المحورية.
  • المتطلبات السابقة.
  • الخطوة التالية.
  • المفاهيم والمراجع ذات الصلة.
  • تمرين أو تطبيق عملي عندما يكون موجودًا.
  • نص رابط وصفي، وليس "اضغط هنا" أو "اقرأ المزيد" وحدها.

1.5 SEO تقني

  • canonical ذاتي وصحيح لكل صفحة مفهرسة.
  • noindex للصفحات الخاصة والبحث الداخلي حسب السياسة الحالية.
  • sitemap تحتوي فقط URLs قانونية قابلة للفهرسة مع lastmod صادق.
  • robots لا يمنع صفحة نحتاج Google أن يقرأ noindex عليها.
  • بيانات JSON-LD تمثل المحتوى المرئي فعلًا ولا تضيف ادعاءات مخفية.
  • اختبار Rich Results لعينة من كل نوع schema بعد أي تغيير قالب.
  • الحفاظ على تحويلات 301 عند الدمج أو تغيير URL.
  • إضافة فحوص CI تدريجيًا لـcanonical، توافق sitemap/indexability، وأنواع schema الأكثر أهمية.

1.6 تجربة الصفحة والأداء

الأهداف الميدانية عند المئين 75 على الجوال وسطح المكتب:

  • LCP ≤ 2.5 ثانية.
  • INP ≤ 200ms.
  • CLS ≤ 0.1.

نبدأ بالقوالب ذات الزيارات الحقيقية، ونقيس بيانات field من Search Console/CrUX قبل تحسينات micro غير مؤثرة.

بوابة الخروج من المرحلة 1

  • أعلى 50 صفحة فرصة تمت مراجعتها وتحسينها أو تصنيفها بقرار واضح.
  • أعلى 5 مسارات لها pillars مكتملة ومترابطة.
  • لا توجد مقالات يتيمة أو روابط مكسورة أو schema مضللة.
  • الصفحات المحسنة تقاس بمقارنة 28 يومًا قبل/بعد، لا بانطباع بصري فقط.

المرحلة 2 — نمو المحتوى المبني على الطلب (الأسابيع 7–12)

الهدف: توسيع السلطة الموضوعية فقط في الأماكن التي أثبتت البيانات حاجتها.

ترتيب أنواع المحتوى

  1. تحديث صفحة قائمة تطابق الاستعلام لكنها لا تجيب عنه جيدًا.
  2. حلول أخطاء برسالة الخطأ الحقيقية، سببها، تشخيصها، الإصلاح، ومنع تكرارها.
  3. مقارنات قرار فيها سيناريو وكود ومعايير، لا جدول سطحي فقط.
  4. تمارين ومشاريع تكمل مسارًا عليه استخدام حقيقي.
  5. Reference لنية lookup واضحة ومميزة.
  6. مسار جديد فقط إذا كانت الفجوة لا يمكن خدمتها بمحتوى موجود.

المرشحون للمستقبل — وليسوا موافقة تلقائية

  • Vue.js، GraphQL، WordPress development، Angular، Spring Boot، وASP.NET.
  • كل مرشح يمر أولًا ببيانات GSC/السوق، اختبار وجود الصفحة، وخريطة معرفة كاملة.
  • AI/ML وAWS وKubernetes وTerraform وTesting وغيرها موجودة حاليًا؛ الأولوية لإكمالها وتحسينها وربطها بدل إعادة إنشائها.

تشغيل backlog المحتوى

  • backlog الحالي مورد تخطيط، وليس أمر نشر.
  • ننتج 5–8 صفحات فقط في الدفعة الواحدة.
  • التسلسل: Validate → Draft → Verify → Review → Link → CI → Human Publish.
  • أي هبوط متكرر في الجودة يوقف الدفعات حتى نعرف السبب.
  • المحتوى الأمني والنسخي والبيانات الواقعية لا يتجاوز بوابته البشرية.

بوابة الخروج من المرحلة 2

  • كل URL جديد له نية مميزة، صفحة أب، روابط دخول، ومؤشر نجاح متوقع.
  • لا cannibalization غير مُدار.
  • المحتوى المنشور الجديد يحقق impressions أو استخدامًا تعليميًا خلال نافذة القياس؛ وإلا يُراجع الافتراض قبل مضاعفة الإنتاج.

المرحلة 3 — التطبيق العملي والعودة (الأشهر 4–6)

الهدف: نقل المنتج من مكتبة ممتازة إلى تجربة تعلّم يعود إليها المستخدم.

3.1 نظام التمارين

  • يبدأ بـHTML وCSS وJavaScript وPython ثم يتوسع حسب الاستخدام.
  • نموذج موحد: المطلوب، starter code، hints، اختبارات، حل تفسيري، مستوى، ومهارة.
  • تصحيح تلقائي حيث يكون آمنًا وقابلًا للتكرار.
  • لا نرسل كودًا غير موثوق إلى خادم الإنتاج إن أمكن تشغيله معزولًا في المتصفح.
  • لوحة تقدم تعرض إتقان المهارات، لا عدد الدروس المفتوحة فقط.

3.2 المشاريع

  • قسم مشاريع منظم: مبتدئ → متوسط → Capstone.
  • أول دفعة: مشروعان أو ثلاثة لأعلى 5 مسارات مثبتة بالبيانات.
  • كل مشروع يحتوي متطلبات، مراحل، معايير قبول، اختبارات، وحلول جزئية.
  • المخرج قابل للمشاركة في portfolio، وهذا يرفع القيمة التعليمية والتحويل.

3.3 تغطية الاختبارات

  • توسيع الاختبارات من 31 إلى المسارات ذات الاستخدام الفعلي أولًا، وليس ملء 51 خانة شكليًا.
  • بنك أسئلة متعدد المستويات مع تفسير الإجابة وتوزيع صعوبة متوازن.
  • منع حفظ الإجابات الصحيحة في واجهة سهلة الاستخراج عندما تصبح الشهادة عالية القيمة.

3.4 العودة

  • "أكمل من حيث توقفت" أكثر وضوحًا في الرئيسية والحساب.
  • أهداف أسبوعية وسلسلة تعلم بسيطة بعد توفر قياس retention.
  • تذكير اختياري، وليس مزعجًا، مع تحكم كامل للمستخدم.
  • نشرة أسبوعية: درس واحد + تمرين + مقال + فرصة؛ لا رسائل يومية آلية.
  • مشاركة الشهادة والإنجاز بصور OG واضحة.

بوابة الخروج من المرحلة 3

  • ارتفاع completion وعودة 7 أيام مقارنة بخط الأساس.
  • مستخدمون حقيقيون يكملون تمرينًا أو مشروعًا، لا مجرد فتح الصفحة.
  • لا gamification بلا أثر تعليمي قابل للقياس.

المرحلة 4 — الدخل بعد إثبات القيمة (الأشهر 6–9)

الهدف: دخل مستدام لا يضعف ثقة المنصة.

4.1 الوظائف والخدمات B2B

  • باقة إعلان وظيفة مدفوعة مع مراجعة، مدة واضحة، وبيانات JobPosting صحيحة.
  • صفحة شركات توضّح الوصول للجمهور والنتائج، مع نموذج تواصل قابل للقياس.
  • لا ننشر وظيفة قديمة أو بلا مصدر أو رابط تقديم صالح.

4.2 Pro

قبل تفعيل Stripe يجب توفر:

  • entitlement server-side واضح ومختبر.
  • قيمة Pro واحدة قوية على الأقل، وليست مجرد badge.
  • صفحة أسعار صادقة، سياسة استرجاع، دعم، وإدارة اشتراك.
  • webhook واختبارات test mode ومراقبة فشل الدفع.
  • حدود استخدام وتكاليف معروفة.

مرشحو قيمة Pro:

  • مساعد يشرح الخطأ أو يراجع محاولة المستخدم بالعربية.
  • feedback أعمق للمشاريع.
  • مختبرات وتحديات متقدمة.
  • تقارير تقدم للجامعات أو الفرق.

لا نجعل الدروس الأساسية خلف الدفع.

4.3 الجامعات والشركات

  • لوحة مجموعة، تعيين مسارات، تقارير تقدم، وإدارة أعضاء.
  • pilot يدوي مع جهة واحدة قبل بناء نظام مؤسسي كامل.

بوابة الخروج من المرحلة 4

  • أول دخل حقيقي مع تتبع مصدره وتكلفته.
  • قيمة مدفوعة يستخدمها العميل، ونسبة دعم وفشل دفع مقبولة.
  • لا تفعيل عام إذا كانت entitlement أو الإلغاء أو الاسترجاع غير مكتملة.

المرحلة 5 — التوسع الذكي (الأشهر 9–12)

الهدف: توسيع ما ثبت نجاحه فقط.

  • تحسين البحث ليعتمد index خفيف وسريع بدل قراءة corpus كامل في كل طلب.
  • مراقبة DB والاستعلامات وإضافة indexes حسب الاستخدام الحقيقي.
  • توسيع المشاريع والتمارين للمسارات الفائزة.
  • توسيع AI tutor ضمن حدود تكلفة وأمان وخصوصية واضحة.
  • تقييم نسخة إنجليزية أو i18n فقط بعد إثبات المنتج العربي، وليس كتشتيت مبكر.
  • تقييم مجتمع Telegram/Discord أو تعليقات بعد تحديد عبء الإشراف.
  • شراكات مع جامعات وبوتكامبات ومجتمعات عربية للحصول على توزيع وروابط طبيعية.

5) نظام SEO التشغيلي

5.1 ما الذي نقيسه أسبوعيًا؟

المجال المؤشرات
الاكتشاف valid sitemap URLs، crawl issues، indexed priority URLs
الظهور impressions، non-brand impressions، queries الجديدة
النقر clicks، CTR حسب الصفحة والاستعلام والجهاز
الترتيب صفحات 1–4، 5–10، 11–20، وأكثر من 20
الجودة صفحات محدثة/مدمجة، أخطاء CI، محتوى يحتاج مراجعة
التجربة LCP، INP، CLS، أخطاء الواجهة
التحويل بدء درس، إكمال درس، اختبار، تسجيل، شهادة، وظيفة، CTA

5.2 دورة العمل الأسبوعية

  1. الاثنين — البيانات: تصدير GSC واختيار الفرص، دون تعديل محتوى.
  2. الثلاثاء — القرار: تعيين Update/Merge/Create/Reject وسبب واضح.
  3. الأربعاء والخميس — التنفيذ: تحسين 5–10 صفحات أو دفعة صغيرة واحدة.
  4. الجمعة — التحقق: CI، build، فحص بصري للجوال، schema، وروابط.
  5. بعد 14 و28 يومًا — القياس: مقارنة نفس الصفحات، لا إجمالي الموقع فقط.

5.3 قائمة فحص الصفحة

  • نية واحدة أساسية ووعد واضح.
  • title وH1 متوافقان لكن غير متطابقين آليًا بلا داعٍ.
  • description تصف الفائدة بصدق.
  • إجابة مبكرة مباشرة، ثم شرح وتطبيق.
  • مثال صحيح تم التحقق منه.
  • أخطاء شائعة أو قرار استخدام عندما يفيد الموضوع.
  • روابط لأب ومتطلب وخطوة تالية.
  • مصدر رسمي للادعاء المتغير.
  • صورة أو مخطط أصلي عندما يشرح أكثر من النص.
  • author/reviewer/date صادقون.
  • canonical وschema وindexability صحيحة.
  • لا تكرار نية أو بنية سطحية مع صفحة أخرى.

5.4 ما لا نفعله في SEO

  • لا نطلب فهرسة 3,853 صفحة يدويًا.
  • لا ننشئ مئات الصفحات من تبديل اسم التقنية داخل قالب واحد.
  • لا نحذف محتوى لمجرد أنه لم يرتب بسرعة.
  • لا نشتري روابط رخيصة ولا ننشر spam في المجتمعات.
  • لا نحشو "بالعربي" أو السنة أو الكلمة المفتاحية بلا طبيعية.
  • لا نضيف schema غير مرئي أو غير مطابق للمحتوى.
  • لا نغيّر التواريخ لإيهام Google بالحداثة.

5.5 مرجع Google الذي نعتمد عليه

  • المحتوى المفيد والموثوق والموجّه للناس
  • أساسيات Google Search
  • دليل SEO للمطورين
  • أفضل ممارسات الروابط
  • إرشادات structured data
  • Core Web Vitals
  • تقارير الأداء في Search Console

7) مؤشرات النجاح

لا نعتمد رقمًا مطلقًا قبل تسجيل baseline. الأهداف التالية مبدئية وتثبت أو تعدل في نهاية المرحلة 0.

المؤشر الرئيسي North Star

عدد المتعلمين الأسبوعيين الذين ينجزون فعلًا ذا معنى: إكمال درس، تشغيل تمرين، اجتياز اختبار، إنهاء مشروع، أو إصدار شهادة.

أهداف 30 يومًا

  • baseline كامل لـGSC والمنتج والأداء.
  • 100% من قوالب الصفحات الأساسية لها عينة فحص indexability/schema.
  • أعلى 20 فرصة SEO لها قرار وتنفيذ أو سبب انتظار.
  • إغلاق المخاطر التشغيلية P0 أو تحويلها إلى مهام محددة المالك والتاريخ.

أهداف 90 يومًا

  • تحسن non-brand clicks بنسبة مبدئية 50% عن baseline، ويعاد ضبط الهدف حسب حجم البيانات الفعلي.
  • تحسن CTR للصفحات المحسنة بنسبة نسبية 20% مع ثبات النية تقريبًا.
  • ≥80% من قائمة URLs ذات الأولوية مفهرسة؛ لا نستخدم كامل sitemap كمقام أعمى.
  • أعلى 50 صفحة فرصة تمت مراجعتها.
  • أول نسخة تمارين ومشاريع تعمل على مسارات مختارة.
  • تحسن واضح في lesson completion و7-day return عن baseline.

أهداف 6 أشهر

  • مضاعفة non-brand organic clicks عن baseline إذا كان القياس مستقرًا.
  • رحلة Search → Lesson → Practice → Quiz قابلة للقياس كاملة.
  • قناة بريدية ذات opt-in ونسبة فتح/نقر قابلة للتحسين.
  • مشاريع فعلية مكتملة ومشتركة من مستخدمين حقيقيين.
  • قرار Go/No-Go موثق لتفعيل Pro أو الوظائف المدفوعة.

أهداف 12 شهرًا

  • نمو عضوي مستدام لا يعتمد على دفعة صفحات واحدة.
  • جمهور عائد، وليس غالبية زيارات لمرة واحدة فقط.
  • أول مصدر دخل مثبت أو قرار واضح بتأجيله بناءً على البيانات.
  • مراقبة ونسخ احتياطي وأمان واختبارات تناسب حجم المنتج.
  • سمعة واضحة كمرجع عربي تطبيقي، تقاس بالبحث عن العلامة والروابط والمشاركة.

8) طريقة تنفيذ العمل بين المالك وCodex وClaude

الأدوار

  • المالك: يحدد الأولوية التجارية، يوافق على النشر/الدفع/الإنتاج، ويوفر بيانات GSC والتحليلات والقرارات الحساسة.
  • Codex: يملك التكامل الهندسي، تعديل الكود، الاختبارات، CI، مراجعة Git، ومنع تضارب التغييرات قبل الدمج.
  • Claude: يُستخدم لمسار مستقل مثل تدقيق ثانٍ، بحث، مراجعة محتوى، أو تنفيذ ملفات لا يعمل عليها Codex في نفس الوقت.

قاعدة عدم التضارب

  • ملف واحد = وكيل واحد في اللحظة نفسها.
  • لا يبدأ Claude وCodex تعديل نفس القالب أو نفس ملف الخطة بالتوازي.
  • المراجعة يمكن أن تكون بالتوازي إذا كانت read-only.
  • لا commit أو push أو deploy أو migration إلا بتكليف صريح.

قالب كل مهمة مسلّمة

Objective:
Scope and allowed files:
Out of scope:
Acceptance criteria:
Required checks:
Do not commit/push/deploy/migrate:
Return: findings, changed files, tests, risks, next action.

Owner chooses outcome
  → Codex divides non-overlapping work
  → Claude performs assigned lane
  → Codex reviews all diffs together
  → one combined CI/build
  → owner approves commit/push/deploy

10) تعريف "تم" لكل نوع عمل

تعديل كود

  • acceptance criteria تحققت.
  • اختبار regression مضاف عندما يكون مناسبًا.
  • typecheck وlint والاختبارات ذات الصلة ناجحة.
  • run-ci.cmd والبناء الكامل ينجحان قبل الدمج الكبير.
  • لا secrets ولا migration غير مطبقة ولا ملفات tooling غير مقصودة في commit.

محتوى أو SEO

  • قرار Create/Merge/Update/Reject موثق.
  • intent والقيمة الفريدة والروابط الداخلية واضحة.
  • الكود والمعلومة والمصادر راجعها المستوى المطلوب.
  • metadata وschema وcanonical وindexability صحيحة.
  • اجتاز CI وفحص الجوال.
  • له baseline وتاريخ قياس بعد النشر.

ميزة منتج

  • تحل مشكلة مستخدم محددة.
  • لها حدث قياس ومؤشر نجاح.
  • حالات الخطأ والتحميل والفراغ والوصولية موجودة.
  • لها owner للتشغيل والدعم.
  • يمكن تعطيلها بأمان إذا سببت مشكلة أو تكلفة غير متوقعة.

  • لا نعلّم بندًا "تم" لأن الكود كُتب فقط؛ يجب أن يجتاز تعريف "تم" أعلاه.
  • التفاصيل اليومية لا تُحشر هنا؛ توضع في تقرير أو issue مرتبط، وتبقى هذه الوثيقة خريطة الاتجاه والقرار.

الخلاصة التنفيذية: نقيس ونثبت أولًا، ثم نحسّن ما يملكه الموقع، ثم نضيف التطبيق العملي والعودة، ثم نفعّل الدخل، وبعدها فقط نتوسع. معيار القرار ليس عدد الصفحات أو الميزات، بل: هل ساعدنا متعلمًا حقيقيًا على الوصول إلى نتيجة أفضل، وهل نستطيع إثبات ذلك بالبيانات؟
