# ADR 0004 — معاملات حقيقية للكتابات الذرّية

- **الحالة:** مقترح — الأداة جاهزة، التبنّي تدريجي
- **التاريخ:** 2026-10-16

## السياق

التطبيق كله على `drizzle-orm/neon-http`: سريع وبدون حالة، ممتاز للقراءة، بس `db.transaction()` بيرمي خطأ. التدقيق لقى مسارات كتابة متعددة الخطوات ممكن تكتمل جزئيًا:

| المسار | الخطر لو انقطع بالنص |
|---|---|
| خط استخراج المناهج | منهج ناقص بالقاعدة (مخفف: طابور المراجعة بيندخل آخرًا) |
| موافقة/رفض/حذف منشور منشئ | تغيير بدون سجل تدقيق |
| التذاكر، المدرّبين، التقارير، التواصل | نفس الشيء |
| التقدّم | إكمالات مش متطابقة مع ملخص التقدّم |

الترحيلات وحدها محمية (`scripts/db-migrate.mjs` بيستخدم WebSocket بمعاملة وحدة). الاشتراكات الشهرية (دفع ← تفعيل ← صلاحيات) ما بتحتمل كتابات جزئية.

## القرار

- `@tcf/db/transaction` بيصدّر `withTransaction(work)`: بيفتح Pool قصير العمر عبر `@neondatabase/serverless` (WebSocket — نفس driver الترحيلات)، بيشغّل الكتابات داخل `BEGIN/COMMIT`، وبيسكّر الـ Pool دايمًا.
- `@tcf/db` (HTTP) بيضل للقراءة وللكتابات المفردة.
- **التبنّي مسار مسار، كل واحد مع اختبار** (PGlite بالاختبارات بيدعم المعاملات) — V2 ما غيّر أي مسار كتابة موجود بصمت. الترتيب المقترح: (1) كل جديد بالاشتراكات، (2) موافقة/رفض منشورات المنشئين + سجل التدقيق، (3) خط المناهج، (4) التقدّم.
- `transaction.ts` على قائمة `SERVER_ONLY`.

## العواقب

اتصال WebSocket لكل معاملة: أبطأ من HTTP بأجزاء من الثانية — مقبول للكتابات النادرة والحساسة، ولا يُستخدم للقراءة.
