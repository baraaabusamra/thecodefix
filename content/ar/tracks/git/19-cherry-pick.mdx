## الموقف

على فرع `develop` ثلاثة commits: بداية لوحة تحكّم جديدة، ثم **إصلاح لانهيار سلّة المشتريات**، ثم رسوم بيانية للوحة. الانهيار يحدث للعملاء الآن، واللوحة لن تجهز قبل أسبوعين. دمج `develop` في `main` ينشر لوحة نصف جاهزة. ما تحتاجه **commit واحد فقط** من الثلاثة.

**`cherry-pick`** يأخذ التغييرات التي أدخلها commit محدّد ويطبّقها كـ commit جديد على الفرع الذي تقف عليه.

## الاستخدام

```bash
git log --oneline develop
# 9b1e4a7 Dashboard charts
# abc8c58 Fix crash on empty cart     ← هذا
# 41d02f3 Start dashboard

git switch main
git cherry-pick -x abc8c58
```

```text
[main 722c4d3] Fix crash on empty cart
```

الإصلاح الآن على `main` وحده، واللوحة بقيت في `develop`.

لاحظ الرقم: `abc8c58` في `develop` صار `722c4d3` في `main`. الـ commit الجديد يحمل **نفس التغيير ونفس الرسالة**، لكنه commit مختلف بأب مختلف. Git لا "ينقل" commits بين الفروع؛ ينسخ تغييراتها.

### لماذا -x؟

```bash
git log -1 --format=%B
```

```text
Fix crash on empty cart

(cherry picked from commit abc8c580685e410bfe4a0f87ce4cb857697f5c0b)
```

`-x` تضيف هذا السطر للرسالة. بعد أشهر، حين يتساءل أحد لماذا يظهر نفس الإصلاح مرتين في التاريخ، يجد الإجابة ورقم الأصل. استخدمها دائمًا حين تنقل إصلاحات بين فروع إصدارات.

## عدّة commits

```bash
git cherry-pick a1b2c3d e4f5g6h       # commits محدّدة، بهذا الترتيب
git cherry-pick B..D                  # من بعد B حتى D: لا يشمل B!
git cherry-pick B^..D                 # من B حتى D: يشمل B
```

صيغة النطاق `B..D` تعني "ما يمكن الوصول إليه من D وليس من B"، فتستبعد `B` نفسه. هذا يفاجئ الجميع مرة واحدة على الأقل. `B^` تعني "الأب الذي قبل B"، فيدخل `B` في النطاق.

## التغييرات بلا commit

```bash
git cherry-pick -n abc8c58           # --no-commit
git status -s
# M  cart.js                          ← مجهّز، بلا commit
```

يطبّق التغييرات ويجهّزها دون أن يحفظ. مفيد لجمع عدّة commits في commit واحد، أو لتعديل الإصلاح قليلًا قبل حفظه على الفرع الجديد.

## عند التعارض

الإصلاح كُتب فوق كود `develop`، وقد يكون `main` مختلفًا في نفس الأسطر:

```bash
# Git يتوقّف ويعلّم الملف المتعارض
# حلّ التعارض كالمعتاد، ثم:
git add cart.js
git cherry-pick --continue

git cherry-pick --skip       # تخطَّ هذا الـ commit (في نطاق من عدّة commits)
git cherry-pick --abort      # ألغِ العملية كلها
```

نفس دورة [حلّ التعارضات](/learn/git/14-conflicts). وإن قال Git:

```text
The previous cherry-pick is now empty, possibly due to conflict resolution.
```

فالتغيير موجود على الفرع أصلًا (ربما انتقاه أحد قبلك)، ولا شيء جديد ليُحفظ. `git cherry-pick --skip`.

## حالات استخدام حقيقية

- **إصلاح عاجل (hotfix)** من فرع تطوير إلى `main` أو فرع إصدار، كما في المثال.
- **نقل إصلاح لإصدار قديم مدعوم:** الإصلاح دُمج في `main`، وتحتاجه أيضًا في `release/2.x` للعملاء الذين لم يرقّوا.
- **commit على الفرع الخطأ:** عملته على `main` بدل فرعك. انتقِه إلى فرعك، ثم احذفه من `main` بـ `reset` إن لم ترفعه ([درس التراجع](/learn/git/04-undo)).
- **إنقاذ commit جيد من فرع مهجور** قبل حذفه.

## متى لا تستخدمه؟

cherry-pick أداة **استثناء**. حين تريد عمل فرع كاملًا، ادمجه. إن وجدت نفسك تنتقي عشرة commits من نفس الفرع كل أسبوع، فسير العمل يحتاج مراجعة: فروع أصغر تُدمج حين تجهز ([استراتيجيات التفرّع](/learn/git/27-branching-strategies)) تلغي الحاجة. فالتغييرات المنتقاة تظهر في التاريخ مرتين، وقد تتعارض حين يُدمج الفرع الأصلي لاحقًا.

## أخطاء شائعة

- **نسيان أنك على الفرع الهدف:** cherry-pick يطبّق حيث تقف. تأكّد بـ `git branch` أولًا.
- **`B..D` وانتظار دخول B:** استخدم `B^..D`.
- **انتقاء commit يعتمد على commits قبله:** يتعارض أو يُترجَم بأخطاء لأن ما بُني عليه غير موجود. انتقِ السلسلة كاملة.
- **انتقاء commit دمج:** يحتاج `-m 1` مثل revert، ونادرًا ما يكون هذا ما تريده فعلًا.
- **الانتقاء بدل الدمج كعادة:** تاريخ مكرّر وتعارضات لاحقة.
