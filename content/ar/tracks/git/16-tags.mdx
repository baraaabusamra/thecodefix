## ما هو الوسم؟

بعد أشهر من التطوير، يسألك عميل: "ما الكود الذي كان يعمل في الإصدار 1.0 الذي ثبّتناه؟". أرقام الـ commits مثل `a2eee82` لا تُحفظ، والفروع تتحرّك مع كل commit جديد. **الوسم (Tag)** اسم ثابت يُعلَّق على commit محدّد **ولا يتحرّك أبدًا**: `v1.0.0` اليوم وبعد خمس سنوات يشير لنفس الـ commit.

| | الفرع | الوسم |
| --- | --- | --- |
| يتقدّم مع commits جديدة | نعم | لا |
| الاستخدام | خطّ عمل مستمر | علامة على لحظة: إصدار، نشر |

## نوعان من الوسوم

```bash
git tag v0.1.0                          # وسم خفيف (Lightweight)
git tag -a v1.0.0 -m "First release"    # وسم مشروح (Annotated)
```

- **الخفيف** مجرّد اسم يشير لـ commit، مثل فرع لا يتحرّك.
- **المشروح** كائن كامل في Git له **صاحب وتاريخ ورسالة** (ويمكن توقيعه رقميًّا بـ `-s`):

```bash
git show v1.0.0
```

```text
tag v1.0.0
Tagger: Baraa <baraa@example.com>
Date:   Sun Oct 18 16:45:08 2026 +0300

First release

commit a2eee821e406a12cd72cd814781981f023017220
...
```

**للإصدارات استخدم المشروح دائمًا.** يعرف من أصدر ومتى ولماذا، وأدوات كثيرة (منها `git describe` و`--follow-tags` أدناه) تعامله كوسم "رسمي" وتتجاهل الخفيف افتراضيًّا. اترك الخفيف للعلامات الشخصية المؤقّتة.

## وسم commit قديم

نسيت وسم الإصدار يوم نشرته؟

```bash
git log --oneline              # ابحث عن الـ commit
git tag -a v0.9.0 9fceb02 -m "Beta release"
```

## عرض الوسوم والبحث فيها

```bash
git tag                         # كلها، بترتيب أبجدي
git tag -l "v1.*"               # بنمط
git tag --sort=-v:refname       # بترتيب الإصدارات، الأحدث أولًا
```

الترتيب الأبجدي يضع `v1.10.0` قبل `v1.9.0`. `--sort=-v:refname` تفهم الأرقام كأرقام إصدارات.

## أين أنا من آخر إصدار؟ git describe

```bash
git describe
```

```text
v1.0.0-2-gc2c46f4
```

اقرأها: "آخر وسم مشروح هو `v1.0.0`، وأنا بعده بـ **2** commit، عند `c2c46f4`" (الحرف `g` يعني git). مشاريع كثيرة تطبع هذا في صفحة "حول" أو في سجلّات الخادم، فيعرف من يرى خطأً أي كود بالضبط يعمل.

## رفع الوسوم

```bash
git push origin v1.0.0          # وسم واحد
git push --follow-tags          # الـ commits + الوسوم المشروحة المرتبطة بها
git push origin --tags          # كل الوسوم المحلية (بحذر)
```

`git push` العادي **لا يرفع الوسوم**. وهذا أشهر سبب لـ "أنشأت الوسم ولا يظهر على GitHub". `--follow-tags` أنظف خيار: يرفع فقط الوسوم المشروحة التي تشير لـ commits ترفعها، فلا يرفع وسومك الخفيفة الشخصية. لجعله افتراضيًّا: `git config --global push.followTags true`.

## العودة إلى إصدار

```bash
git switch --detach v1.0.0      # أو: git checkout v1.0.0
```

تصبح في حالة **detached HEAD** على كود ذلك الإصدار ([درس الفروع](/learn/git/02-branches)): شغّله، ابحث عن خطأ، قارن. لإصلاح خطأ في إصدار قديم، أنشئ فرعًا منه:

```bash
git switch -c hotfix/1.0.1 v1.0.0
```

## حذف وسم

```bash
git tag -d v0.1.0                   # محليًّا
git push origin --delete v0.1.0     # على البعيد
```

> ⚠️ **لا تنقل وسمًا منشورًا.** إن أخطأت في `v1.0.0` بعد رفعه، لا تحذفه وتعيد إنشاءه على commit آخر: من نزّله سابقًا يحتفظ بالقديم، وأنظمة البناء ومديرو الحزم يخزّنونه. أصدر `v1.0.1` بدلًا منه.

## الترقيم الدلالي (Semantic Versioning)

العُرف الأوسع لأسماء الإصدارات: **`vMAJOR.MINOR.PATCH`**

| الرقم | يزيد حين | مثال |
| --- | --- | --- |
| **MAJOR** | تغيير يكسر التوافق: من يستخدمك يحتاج تعديل كوده | `v1.4.2` ← `v2.0.0` |
| **MINOR** | ميزة جديدة متوافقة | `v1.4.2` ← `v1.5.0` |
| **PATCH** | إصلاح خطأ فقط | `v1.4.2` ← `v1.4.3` |

الرقم وعد لمن يعتمد على مشروعك: ترقية PATCH آمنة دائمًا، وMAJOR تتطلّب قراءة ما تغيّر.

## GitHub Releases

صفحة **Releases** على GitHub مبنية على الوسوم: كل Release يرتبط بوسم، وتضيف إليه ملاحظات الإصدار وملفات جاهزة للتنزيل (برنامج مبني، ملف مضغوط). وكثير من أنظمة النشر (CI) تبدأ عملية النشر تلقائيًّا حين يُرفع وسم يبدأ بـ `v`.

## أخطاء شائعة

- **`git push` وانتظار ظهور الوسم:** الوسوم تحتاج دفعًا صريحًا أو `--follow-tags`.
- **وسوم خفيفة للإصدارات:** بلا صاحب ولا تاريخ، و`git describe` يتجاهلها افتراضيًّا.
- **نقل وسم منشور:** أصدر رقمًا جديدًا.
- **`v1.0` و`1.0.0` و`version-1` في نفس المشروع:** اختر صيغة واحدة والتزم بها.
- **`git push --tags` بلا تفكير:** يرفع كل وسم تجريبي محلي عندك.

> 🎯 التالي: إعادة الأساس (Rebase).
