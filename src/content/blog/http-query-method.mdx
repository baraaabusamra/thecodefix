كل مطوّر REST API واجه هالموقف: عندك بحث معقّد بفلاتر متعددة أو قائمة معرّفات طويلة، وGET ما بيكفي (طول الرابط محدود عمليًا، ولا جسم رسمي). الحل التقليدي: `POST /articles/search`. يشتغل، بس بيفقّد الطلب صفة الأمان والتخزين المؤقت رغم إنه فعليًا مجرد قراءة. بيونيو 2026، **RFC 10008** قدّم حل رسمي: طريقة HTTP جديدة اسمها **QUERY**.

## المشكلة يلي بقيت من أيام HTTP الأولى

- **GET** آمنة (Safe)، عديمة الأثر التراكمي (Idempotent)، وقابلة للتخزين المؤقت — بس بلا جسم طلب رسمي، فالاستعلامات المعقّدة تضطرك تحشرها بمعاملات رابط محدودة الطول.
- **POST** بتحمل جسم كامل بلا حدود عملية — بس مش آمنة ولا idempotent، فالمتصفحات والوسطاء يتعاملون معها وكأنها ممكن تُغيّر بيانات، حتى لو كانت فعليًا مجرد بحث.

النتيجة: أي استعلام بحث معقّد كان يخسر إما إمكانية التخزين المؤقت (لو استُخدم POST)، أو إمكانية حمل بيانات معقّدة (لو استُخدم GET).

## QUERY: أول طريقة HTTP جديدة منذ 16 سنة

RFC 10008 عرّفت **QUERY** — أول طريقة HTTP قياسية جديدة تُسجَّل منذ `PATCH` (RFC 5789، سنة 2010). QUERY آمنة وعديمة الأثر التراكمي وقابلة للتخزين المؤقت متل GET، لكن بتحمل جسم طلب كامل متل POST:

```
QUERY /api/articles HTTP/1.1
Content-Type: application/x-www-form-urlencoded

status=published&author=42&tags=rest,api

// الاستجابة
HTTP/1.1 200 OK
Content-Type: application/json

[{ "id": 1, "title": "مقال منشور" }]
```

الخادم يُعلن صيغ الجسم المقبولة عبر ترويسة جديدة، `Accept-Query`، عادة ضمن ردّ OPTIONS.

## مقارنة سريعة

| | GET | POST (كحيلة بحث) | QUERY |
|---|---|---|---|
| آمنة (Safe) | ✅ | ❌ | ✅ |
| عديمة الأثر التراكمي | ✅ | ❌ | ✅ |
| قابلة للتخزين المؤقت | ✅ | ❌ عادة | ✅ |
| تحمل جسم طلب كامل | ❌ | ✅ | ✅ |
| حدود طول الرابط | نعم | لا | لا |

## متى تستخدمها؟

استخدم QUERY حين يكون الاستعلام معقّدًا جدًا بحيث لا يناسبه رابط GET قصير — فلاتر متعددة، شروط متداخلة، أو قائمة معرّفات طويلة. لأي طلب بسيط (صفحة، ترتيب، فلتر واحد أو اثنين)، GET يبقى الخيار الافتراضي.

## هل تعتمد عليها اليوم؟

QUERY حديثة جدًا وقت كتابة هالمقال. المواصفة رسمية ومعتمدة من IETF، بس الدعم الفعلي بمكتبات الخادم (متل Node.js) والمتصفحات لا يزال يتوسّع تدريجيًا. قبل ما تعتمد عليها بمشروع إنتاجي، تحقّق فعليًا من دعم الأدوات يلي تستخدمها — لو ما توفّر الدعم بعد، حيلة `POST /search` تبقى بديل عملي مقبول مؤقتًا، بس وثّق بوضوح إنها ليست آمنة ولا idempotent حتى لا يتعامل معها العميل بافتراضات خاطئة.
