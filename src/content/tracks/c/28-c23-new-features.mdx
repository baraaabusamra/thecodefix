## ليش C23 مهم الآن؟

بدءًا من إصدار GCC 15 صار المعيار الافتراضي عند الترجمة هو **C23** (`-std=gnu23`) بدل C17 — يعني لما تكتب `gcc program.c -o program` بدون تحديد معيار صراحة، أنت فعليًا تترجم بـ C23. GCC 16 وسّع الدعم أكثر (مثل النوع `_BitInt`). هذا يفتح مزايا جديدة تستحق معرفتها حتى لو كنت تتبع نفس أسلوب الدروس السابقة.

> 💡 مزايا اللغة نفسها (مثل `bool` أو `nullptr` بالأسفل) يكفيها مترجم يدعم C23. لكن **دوال المكتبة القياسية الجديدة** (القسم الأخير بهذا الدرس) تحتاج كمان مكتبة C محدَّثة تدعمها فعليًا — على لينوكس هذا يعني glibc، ودعمها لهذه الدوال وصل مؤخرًا بإصدار **glibc 2.43** (يناير 2026).

> 💡 لو تبي تجبر معيار محدد بدل الافتراضي (مثلًا للتوافق مع كود قديم)، استخدم `gcc -std=c17 program.c` أو `-std=c23` صراحة.

## bool و true و false صارت كلمات مفتاحية

في الدرس عن أنواع البيانات تعلّمت إنه لازم تضمّن `<stdbool.h>` عشان تستخدم `bool`. من C23، `bool` و`true` و`false` جزء من اللغة نفسها مباشرة، بدون أي تضمين:

```c
bool active = true;   // يعمل مباشرة في C23، بدون #include <stdbool.h>
```

`<stdbool.h>` ما زال موجود ويعمل بدون مشاكل (للتوافق مع كود أقدم)، لكنه لم يعد ضروريًا بمشروع C23 جديد.

## nullptr بدل NULL

`NULL` تقليديًا مجرد ماكرو (غالبًا `((void*)0)` أو `0`)، وهذا يسبب التباس أحيانًا لأنه يمكن التعامل معه كعدد صحيح بالخطأ. C23 يضيف `nullptr`: قيمة بنوع مخصّص `nullptr_t` تتحوّل تلقائيًا لأي نوع مؤشّر، ولا يمكن الخلط بينها وبين رقم:

```c
int *p = nullptr;   // أوضح من NULL، ومضمون أنه مؤشّر لا عدد صحيح
```

## constexpr لثوابت تُحسب وقت الترجمة

```c
constexpr int maxUsers = 100;
constexpr double pi = 3.14159;
```

بعكس `#define` (استبدال نصّي بلا نوع)، متغيّر `constexpr` له نوع حقيقي يفحصه المترجم. وبعكس `const` العادي — اللي ممكن تُهيّأ بقيمة تُحسب وقت التشغيل — قيمة `constexpr` يجب أن تأتي من تعبير ثابت يُحسب بالكامل وقت الترجمة.

## typeof لاشتقاق نوع متغيّر موجود

```c
int x = 5;
typeof(x) y = 10;   // y من نوع int تلقائيًا، بدون كتابة int صراحة
```

مفيد بالماكروهات العامة حيث تحتاج تعريف متغيّر بنفس نوع متغيّر آخر دون معرفة اسم ذلك النوع مسبقًا.

## فواصل رقمية لقراءة أوضح

```c
long long distance = 299'792'458;   // سرعة الضوء - أوضح من 299792458
int mask = 0xFF'FF'00'00;
```

علامة `'` بين الأرقام تُتجاهل تمامًا وقت الترجمة، وتُستخدم فقط لتحسين قراءة الأرقام الكبيرة — لا تغيّر القيمة الفعلية بأي شكل.

## سمات معيارية [[...]]

C23 يضيف سمات (attributes) موحّدة بين كل المترجمات، بدل الاعتماد على امتدادات خاصة بـ GCC أو Clang:

```c
[[deprecated("استخدم newFunc بدلها")]]
void oldFunc(void);

[[maybe_unused]] int debugCounter = 0;

[[nodiscard]] int mustCheckResult(void);

switch (x) {
    case 1:
        doSomething();
        [[fallthrough]];   // انزلاق متعمّد، ليس نسيان break
    case 2:
        doMore();
        break;
}
```

- **`[[deprecated]]`**: يحذّرك المترجم لو استدعيت دالة أو استخدمت نوعًا قديمًا.
- **`[[maybe_unused]]`**: يمنع تحذير "متغيّر غير مستخدم" لمتغيّر تعرف أنه قد لا يُستخدم بكل المسارات.
- **`[[nodiscard]]`**: يحذّرك لو تجاهلت القيمة المُرجعة من دالة (مفيد لدوال شبيهة بـ malloc أو fopen يجب فحص نتيجتها).
- **`[[fallthrough]]`**: يوضّح أن الانزلاق بين حالتَي switch متعمّد، لا نسيان لـ break.

## دوال قياسية جديدة من C23 وصلت مع glibc 2.43

الميزات السابقة كلها تخص صياغة اللغة نفسها. لكن معيار C23 أضاف أيضًا دوالًا جديدة للمكتبة القياسية، وهذه لا تكفيها ترقية المترجم فقط — تحتاج مكتبة C فعلية تنفّذها. على لينوكس، `glibc 2.43` أضافت دعمها.

### memset_explicit: مسح ذاكرة حسّاسة فعلًا

`memset` العادية تُهيّئ منطقة ذاكرة بقيمة معيّنة — لكن المترجم يملك صلاحية حذفها بالكامل (dead-store elimination) لو رأى أنه لا قراءة لاحقة على تلك الذاكرة، حتى لو كانت تحتوي كلمة مرور أو مفتاح تشفير كنت تحاول محوه فعلًا قبل تحرير الذاكرة:

```c
#include <string.h>

char password[64] = "secret";
// ...استخدام password...
memset(password, 0, sizeof(password));   // قد يُحذف بالكامل من المترجم!
```

`memset_explicit` من C23 تحل هذه المشكلة: نفس التوقيع، لكن المعيار يُلزم المترجم بتنفيذها فعليًا دائمًا، بلا حذف مهما كانت التحسينات (`optimization`) مفعّلة:

```c
#include <string.h>

char password[64] = "secret";
// ...استخدام password...
memset_explicit(password, 0, sizeof(password));   // مضمون التنفيذ دائمًا
```

### free_sized و free_aligned_sized: تحرير ذاكرة بمعرفة حجمها مسبقًا

`free` العادية تأخذ المؤشّر فقط، وتعتمد داخليًا على معلومات مخزَّنة مسبقًا بالكومة (heap) لمعرفة حجم الكتلة المطلوب تحريرها. C23 يضيف `free_sized` (لتحرير ذاكرة من `malloc`/`calloc`/`realloc`) و`free_aligned_sized` (لذاكرة من `aligned_alloc`)، حيث تمرّر الحجم بنفسك:

```c
#include <stdlib.h>

int *arr = malloc(10 * sizeof(int));
// ...استخدام arr...
free_sized(arr, 10 * sizeof(int));   // نفس أثر free(arr)، مع تمرير الحجم صراحة
```

تمرير الحجم صراحة يفتح المجال لمخصّص ذاكرة (allocator) لتحرير أسرع في بعض الحالات، لكنه **ليس إلزاميًا للاستخدام اليومي** — `free` العادية تبقى كافية لمعظم الكود، وهذه دوال إضافية للحالات التي تعرف فيها الحجم أصلًا.

> 💡 هذه الدوال تحتاج مكتبة C محدَّثة فعليًا (glibc 2.43 فما فوق)، وليس فقط مترجمًا يدعم C23 — تأكد من إصدار glibc على بيئة التشغيل قبل الاعتماد عليها بمشروع حقيقي.

## أخطاء شائعة

- افتراض أن كل المترجمات تدعم C23 كاملًا — تأكد من إصدار GCC أو Clang قبل الاعتماد على هذه المزايا بمشروع فعلي، خصوصًا لو المشروع يُبنى ببيئات أقدم.
- الظن أن `constexpr` في C تعمل تمامًا مثل C++ — نسخة C23 أكثر محدودية (متغيّرات فقط، لا دوال `constexpr`).
- استخدام `nullptr` بدل `NULL` بدوال قديمة variadic (مثل `execl`) دون تحويل صريح عند الحاجة — راجع توثيق الدالة قبل الاعتماد على التحويل التلقائي.
- الخلط بين دعم المترجم لميزة لغوية (يكفيه `-std=c23`) ودعم المكتبة لدالة جديدة مثل `memset_explicit` (يحتاج إصدار glibc محدَّثًا فعليًا على بيئة التشغيل، لا فقط بيئة الترجمة).
