## ما هو OWASP ASVS؟

ASVS (Application Security Verification Standard) هو معيار من OWASP يحدد متطلبات أمان التطبيقات ومستويات الضمان المختلفة. يساعد الفرق على بناء تطبيقات آمنة وتقييم مستوى الأمان الحالي.

> 💡 الإصدار الحالي هو **ASVS 5.0** (صدر في مايو 2025) — وهو أكبر إعادة هيكلة يشهدها المعيار منذ إصدار 4.0 عام 2019. عدد الفصول ارتفع من 14 إلى 17، وعدد المتطلبات من نحو 286 إلى نحو 350، وتغيّرت معرّفات كل متطلب تقريبًا بسبب إعادة الترتيب. إذا رأيت مشروعًا أو أداة لا تزال تشير لأرقام فصول 4.0 (مثل V1 Architecture أو V13 API & Web Service) فهي تستخدم نسخة قديمة.

```text
ASVS ليس مجرد قائمة فحص - إنه إطار عمل متكامل للأمان التطبيقي (هيكلة 5.0):
  - V1: Encoding and Sanitization (الترميز والتعقيم)
  - V2: Validation and Business Logic (التحقق ومنطق الأعمال)
  - V3: Web Frontend Security (أمان الواجهة الأمامية) — فصل جديد
  - V4: API and Web Service (واجهات API وخدمات الويب)
  - V5: File Handling (التعامل مع الملفات)
  - V6: Authentication (المصادقة)
  - V7: Session Management (إدارة الجلسات)
  - V8: Authorization (التفويض/الصلاحيات)
  - V9: Self-contained Tokens (الرموز ذاتية الاحتواء مثل JWT) — فصل جديد
  - V10: OAuth and OIDC — فصل جديد
  - V11: Cryptography (التشفير)
  - V12: Secure Communication (الاتصال الآمن)
  - V13: Configuration (الإعدادات)
  - V14: Data Protection (حماية البيانات)
  - V15: Secure Coding and Architecture (البرمجة والمعمارية الآمنة) — فصل جديد
  - V16: Security Logging and Error Handling (التسجيل الأمني ومعالجة الأخطاء)
  - V17: WebRTC — فصل جديد
```

الفصول الأربعة الجديدة كليًا في 5.0 هي: Web Frontend Security، Self-contained Tokens، OAuth and OIDC، وWebRTC — تعكس واقع التطبيقات الحديثة (SPA، JWT كمعيار فعلي، تسجيل دخول موحّد، اتصال فيديو/صوت مباشر بالمتصفح). في المقابل حُذف فصل Architecture المستقل (V1 في 4.0) ووُزّع محتواه على فصول أخرى، ودُمجت متطلبات التحقق من المدخلات (Input Validation) مع منطق الأعمال (Business Logic) في فصل واحد بدل فصلين منفصلين.

## مستويات الضمان

| المستوى | الوصف | لمن؟ |
|---------|-------|------|
| **L1** | أساسي (Automated) | كل التطبيقات - ثغرات يمكن اكتشافها تلقائياً |
| **L2** | قياسي (Manual) | تطبيقات تتعامل مع بيانات حساسة - يحتاج مراجعة يدوية |
| **L3** | متقدم (In-Depth) | تطبيقات عالية الخطورة (بنوك، صحة، أمن وطني) |

> 💡 في نسخة 5.0 أُعيد ضبط توزيع المتطلبات بين المستويات بشكل ملحوظ: في 4.0.3 كانت متطلبات L1 نحو 46% من الإجمالي (128 من 278)، بينما في 5.0 أصبحت نحو 20% فقط (70 من 350). الهدف تخفيف عبء L1 ليكون "خط دفاع أول" سهل التبني، مقابل توسّع كبير في نطاق L3 للتطبيقات عالية الخطورة. النسخة الجديدة أضافت أيضًا مفهوم **Documented Security Decisions**: كل فصل يبدأ الآن بمتطلبات توثيق صريحة — لماذا اخترتَ ضابطًا أمنيًا معينًا وكيف طبّقته — بدل ترك القرار ضمنيًا كما كان في 4.0.

### المستوى 1 (L1) - أساسي

```javascript
// مفهوم متطلبات L1 (أساسية، قابلة للاختبار الآلي)
{
  "Authentication": {
    note: "تأكد أن نماذج المصادقة تستخدم HTTPS فقط، ولا توجد كلمات مرور افتراضية",
  },
  "ValidationAndBusinessLogic": {
    note: "تأكد من validation لكل المدخلات ومن استخدام parameterized queries",
  },
}
```

### المستوى 2 (L2) - قياسي

```javascript
// مفهوم متطلبات L2 (كل L1 + متطلبات تحتاج مراجعة يدوية)
{
  "Authentication": {
    note: "MFA للحسابات الحساسة، تخزين كلمات المرور بـ bcrypt/argon2، session timeout",
  },
  "SessionManagement": {
    note: "session IDs عشوائية، إبطال الجلسة بعد logout، HttpOnly + Secure cookies",
  },
  "ApiAndWebService": {
    note: "مصادقة كل API endpoints، التحقق من الصلاحية لكل كائن (BOLA)، Rate Limiting",
  },
}
```

### المستوى 3 (L3) - متقدم

```javascript
// مفهوم متطلبات L3 (كل L1 + L2 + متطلبات متقدمة، نطاقها توسّع كثيرًا في 5.0)
{
  "SecureCodingAndArchitecture": {
    note: "threat model موثّق للتطبيق، قرارات أمنية موثّقة لكل فصل (Documented Security Decisions)",
  },
  "SecurityLoggingAndErrorHandling": {
    note: "تسجيل كل محاولات المصادقة، معالجة آمنة للحالات الاستثنائية بلا تسريب معلومات",
  },
}
```

> ⚠️ لا تعتمد على أرقام متطلبات محفوظة عن ظهر قلب (مثل "13.1.1") — معرّفات 5.0 مختلفة تمامًا عن 4.0 بسبب إعادة الترتيب الكاملة. ارجع دائمًا لنسخة المعيار الحالية على GitHub (OWASP/ASVS) عند تطبيق متطلب محدد.

## تطبيق ASVS في التطوير

### مرحلة التخطيط

```javascript
// اختيار المستوى المناسب
function determineAsvsLevel(application) {
  const { dataType, users, impact } = application;

  if (impact === 'critical') return 'L3'; // بنوك، صحة
  if (dataType.includes('personal') || users > 100000) return 'L2';
  return 'L1'; // مواقع بسيطة
}

// متطلبات ASVS حسب الفصل (هيكلة 5.0) في ملف Requirements
const asvsRequirements = {
  L1: ['Authentication', 'ValidationAndBusinessLogic', 'Configuration'],
  L2: ['L1', 'SessionManagement', 'Authorization', 'ApiAndWebService', 'Cryptography'],
  L3: ['L2', 'SecureCodingAndArchitecture', 'SecurityLoggingAndErrorHandling', 'DataProtection'],
};
```

### مرحلة التطوير

```javascript
// استخدام ASVS في PR Review
module.exports = {
  rules: {
    'require-auth': {
      meta: { severity: 'error' },
      create(context) {
        return {
          MethodDefinition(node) {
            // ASVS V4 (API and Web Service): تأكد من وجود middleware auth على API
            if (isAPIRoute(node)) {
              const hasAuth = node.value.body.body.some(
                stmt => isAuthMiddleware(stmt)
              );
              if (!hasAuth) {
                context.report({
                  node,
                  message: 'ASVS V4: API endpoint بدون مصادقة',
                });
              }
            }
          },
        };
      },
    },
  },
};
```

### مرحلة الاختبار

```javascript
// اختبار ASVS تلقائي (مصنّف حسب فصل 5.0)
const asvsTests = {
  'V6-Authentication': {
    name: 'HTTPS فقط للمصادقة',
    test: async (url) => {
      const res = await fetch(url.replace('http://', 'https://'));
      return res.ok;
    },
    severity: 'critical',
  },
  'V2-ValidationAndBusinessLogic': {
    name: 'Parameterized Queries',
    test: async (url) => {
      // SQLi test
      const res = await fetch(`${url}?id=1' OR '1'='1`);
      return res.status === 400 || res.status === 500;
    },
    severity: 'critical',
  },
  'V8-Authorization': {
    name: 'BOLA Protection',
    test: async (baseUrl, token) => {
      // اختبار IDOR
      const res1 = await fetch(`${baseUrl}/api/users/1`, {
        headers: { Authorization: `Bearer ${token}` },
      });
      const res2 = await fetch(`${baseUrl}/api/users/999`, {
        headers: { Authorization: `Bearer ${token}` },
      });
      return res1.status !== res2.status;
    },
    severity: 'high',
  },
};
```

## ASVS و OWASP Top 10

```text
منذ نوفمبر 2025 صدرت أيضًا نسخة جديدة من OWASP Top 10 العام (خاص بتطبيقات الويب عمومًا لا الـ API فقط)،
بعد أن ظل إصدار 2021 هو المرجع لسنوات. لاحظ أن SSRF لم يعد بندًا مستقلاً في هذه القائمة العامة —
دُمج ضمن Broken Access Control — لكنه لا يزال بندًا مستقلاً ومهمًا في OWASP API Security Top 10 (2023)
الخاص بالـ APIs تحديدًا، والذي يعتمد عليه هذا المسار بشكل أساسي (راجع درس تهديدات API).
```

| OWASP Top 10 2025 | ASVS Sections ذات الصلة |
|-------------------|------------------------|
| A01: Broken Access Control (يشمل SSRF الآن) | V8 (Authorization), V4 (API and Web Service) |
| A02: Security Misconfiguration | V13 (Configuration) |
| A03: Software Supply Chain Failures | V15 (Secure Coding and Architecture) |
| A04: Cryptographic Failures | V11 (Cryptography), V14 (Data Protection) |
| A05: Injection | V1 (Encoding and Sanitization), V2 (Validation and Business Logic) |
| A06: Insecure Design | V15 (Secure Coding and Architecture) |
| A07: Authentication Failures | V6 (Authentication), V9 (Self-contained Tokens), V10 (OAuth and OIDC) |
| A08: Software or Data Integrity Failures | V14 (Data Protection), V15 (Secure Coding and Architecture) |
| A09: Security Logging and Alerting Failures | V16 (Security Logging and Error Handling) |
| A10: Mishandling of Exceptional Conditions (فئة جديدة كليًا) | V16 (Security Logging and Error Handling) |

> 💡 الجدول أعلاه ربط منطقي بين موضوعات كل فئة وأقرب فصول ASVS 5.0 لها للتوضيح، وليس تعيينًا رسميًا حرفيًا من OWASP — المعيار الرسمي لا ينشر جدول تطابق 1:1 بين المشروعين.

## أدوات ASVS

```bash
# استنساخ المستودع الرسمي لمراجعة المتطلبات الكاملة لنسخة 5.0
git clone https://github.com/OWASP/ASVS
cd ASVS/5.0/en
# كل فصل ملف Markdown مستقل، مثل 0x15-V6-Authentication.md
```

```javascript
// أداة ASVS بسيطة (مبنية على ملف متطلبات JSON خاص بفريقك، وليس ملفًا رسميًا من OWASP)
const asvs = require('./asvs-5.0.json');

function generateChecklist(level = 'L1') {
  const requirements = [];

  for (const [section, items] of Object.entries(asvs)) {
    for (const [id, req] of Object.entries(items)) {
      if (req.levels.includes(level)) {
        requirements.push({
          id,
          title: req.title,
          description: req.description,
          section: req.section,
          level,
        });
      }
    }
  }

  return requirements;
}
```

## شهادة ASVS

```text
للحصول على شهادة ASVS:
  1. حدد مستوى الضمان (L1, L2, L3)
  2. قيم تطبيقك حسب المتطلبات
  3. وثق النتائج والأدلة (بما فيها Documented Security Decisions لكل فصل في 5.0)
  4. راجع مع خبراء (اختياري)
  5. انشر التقرير (اختياري)

مستويات الشهادة:
  ✅ ASVS Level 1 Verified
  ✅✅ ASVS Level 2 Verified
  ✅✅✅ ASVS Level 3 Verified
```

> ⚠️ ASVS ليس مشروعاً لمرة واحدة - إنه عملية مستمرة. كل تحديث أو ميزة جديدة في تطبيقك قد تؤثر على مستوى الامتثال لـ ASVS، وكل قفزة إصدار كبيرة (مثل 4.0 إلى 5.0) تستحق مراجعة كاملة لأن المعرّفات والهيكلة تتغيّر لا التفاصيل فقط.
