## فجوة قديمة بعمر HTTP نفسه

من درس [طرق HTTP](/learn/rest-api/04-http-methods) بتعرف إنه `GET` آمنة (Safe) وعديمة الأثر التراكمي (Idempotent) وقابلة للتخزين المؤقت — بس ما بتحمل جسم طلب رسمي، فأي استعلام معقّد (فلاتر متعددة، قائمة معرّفات طويلة، شروط متداخلة) لازم يتحشر بمعاملات رابط (query params) محدودة الطول عمليًا.

الحل الشائع كان: `POST /articles/search`. يشتغل تقنيًا، بس `POST` مش آمنة ولا idempotent — فالمتصفحات والوسطاء (proxies, CDNs) بيتعاملوا معها وكأنها قد تُغيّر بيانات، حتى لو كانت فعليًا مجرد بحث. النتيجة: لا تخزين مؤقت تلقائي، ولا إعادة محاولة آمنة عند انقطاع الشبكة.

## QUERY — الحل الرسمي (RFC 10008)

بيونيو 2026 نشرت IETF **RFC 10008** يلي يعرّف طريقة HTTP جديدة اسمها **QUERY** — وهي أول طريقة HTTP قياسية جديدة تُسجَّل منذ `PATCH` سنة 2010 (فجوة 16 سنة كاملة).

QUERY بتجمع خاصيتين كانوا يبدوا متناقضين:

| | GET | POST (كحيلة بحث) | QUERY |
|---|---|---|---|
| آمنة (Safe) | ✅ | ❌ | ✅ |
| عديمة الأثر التراكمي | ✅ | ❌ | ✅ |
| قابلة للتخزين المؤقت | ✅ | ❌ عادة | ✅ (عبر Accept-Query) |
| تحمل جسم طلب كامل | ❌ | ✅ | ✅ |

بما إنها آمنة، المتصفح أو أي وسيط شبكة يقدر يعيد محاولتها تلقائيًا بأمان لو فشلت الشبكة، ويخزّن ردّها مؤقتًا — تمامًا متل GET، بس بدون قيود طول الرابط.

## بنية الطلب

```
QUERY /api/articles HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Accept: application/json

status=published&author=42&tags=rest,api

// الاستجابة
HTTP/1.1 200 OK
Content-Type: application/json

[{ "id": 1, "title": "مقال منشور" }]
```

جسم الطلب يوصف الاستعلام بالصيغة التي يحدّدها المورد — غالبًا `application/x-www-form-urlencoded` أو JSON، مو صيغة واحدة إجبارية تفرضها المواصفة.

## Accept-Query — كيف يُعلن الخادم دعمه

المواصفة تضيف ترويسة جديدة، `Accept-Query`، يستخدمها الخادم ليُعلن الصيغ التي يقبلها لجسم QUERY — عادة ضمن ردّ `OPTIONS`:

```
OPTIONS /api/articles HTTP/1.1

// الاستجابة
HTTP/1.1 204 No Content
Allow: GET, POST, QUERY, OPTIONS
Accept-Query: application/x-www-form-urlencoded, application/json
```

> 💡 هاي بالضبط نفس فكرة ترويسة Allow يلي تعلّمتها بمرجع OPTIONS — بس مخصّصة لصيغة جسم QUERY تحديدًا.

## متى تستخدمها؟

- استعلام بحث معقّد بفلاتر متعددة يصعب التعبير عنه بمعاملات رابط قصيرة.
- قائمة معرّفات طويلة (مثلًا "أعطني كل المقالات اللي IDs متلها ضمن هالقائمة الطويلة") لا تناسب حدود طول الرابط العملية.
- أي حالة كنت سابقًا تلجأ فيها لـ `POST /search` كحيلة، بس تحتاج فعليًا سلوك آمن قابل للتخزين المؤقت.

> ⚠️ ما زالت GET المعاملات القصيرة (صفحة، ترتيب، فلتر بسيط) هي الخيار الافتراضي — راجع [درس معاملات الاستعلام](/learn/rest-api/10-query-params). QUERY حل لحالة محدّدة: استعلامات معقّدة يصعب التعبير عنها برابط قصير، مو بديل عام عن GET.

## جاهزيتها اليوم

QUERY حديثة جدًا وقت كتابة هالدرس (نُشرت رسميًا يونيو 2026). قبل ما تعتمد عليها بمشروع إنتاجي:

- تحقّق فعليًا أن إطار العمل والخادم (Node.js، Express أو غيره) ومكتبات العميل يدعموها فعليًا، لا افتراض نظري بمجرد قراءة المواصفة.
- دعم النماذج (`<form method="query">`) والتخزين المؤقت الفعلي بالمتصفحات لا يزال قيد التطوّر ومتفاوت — لا تعتمد عليه لواجهة عامة اليوم بدون اختبار مباشر.
- لو ما توفّر الدعم بعد، `POST /search` تبقى حيلة عملية مقبولة مؤقتًا — فقط وثّق بوضوح أنها ليست آمنة/idempotent حتى لا يتعامل معها العميل وكأنها كذلك.

## خلاصة

QUERY سدّت فجوة موجودة بـ HTTP من يوم ما نشأ: طريقة آمنة، عديمة الأثر التراكمي، وقابلة للتخزين المؤقت — لكن قادرة تحمل جسم طلب كامل متل POST. لسا بمراحلها الأولى من الانتشار، بس هي الاتجاه الرسمي المستقبلي لاستعلامات REST المعقّدة بدل حيلة "POST كبحث".
