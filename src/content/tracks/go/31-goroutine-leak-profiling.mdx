> نفس المشكلة اللي حذّرنا منها هناك (تشغيل goroutine بلا طريقة لإيقافها)،
> لكن هنا أداة رسمية من Go نفسها تكتشفها تلقائيًا بدل ما تعتمد على مراجعة
> الكود يدويًا.

## مشكلة صعبة الاكتشاف يدويًا

goroutine **مسرَّبة (leaked)** هي goroutine محجوبة للأبد على قناة أو
`sync.Mutex` أو `sync.Cond` أو `sync.WaitGroup.Wait` — بانتظار حدث لن
يصل أبدًا. البرنامج يستمرّ بالعمل ظاهريًا، لكن كل goroutine مسرَّبة تستهلك
ذاكرتها (~2 كيلوبايت فأكثر) للأبد، وبخادم طويل التشغيل يتراكم هذا حتى
يستهلك الذاكرة بالكامل.

```go
func leaky() {
  ch := make(chan int) // بلا buffer، وبلا أي مُرسِل لها لاحقًا
  go func() {
    <-ch // goroutine تنتظر هنا للأبد — لا أحد سيرسل على ch
  }()
} // الدالة تعود، ch تصبح غير قابلة للوصول، لكن الـ goroutine ما زالت حيّة ومحجوبة
```

قبل الآن، اكتشاف هذا يعتمد على مراجعة كود دقيقة أو ملاحظة نمو تدريجي
بعدد الـ goroutines (`runtime.NumGoroutine()`) بمرور الوقت — بدون معرفة
أيّها بالضبط ولا مكانها بالكود.

## الحل: بروفايل goroutineleak

منذ **Go 1.27** (أغسطس 2026)، حزمة `runtime/pprof` توفّر بروفايلًا جاهزًا
اسمه `goroutineleak` — مستقرّ بالكامل، بلا حاجة لأي علم تجريبي (كان
تجريبيًا خلف `GOEXPERIMENT=goroutineleakprofile` بـ Go 1.26 فقط).

```go
import (
  "os"
  "runtime/pprof"
)

func dumpLeaks() {
  f, _ := os.Create("leaks.pprof")
  defer f.Close()
  pprof.Lookup("goroutineleak").WriteTo(f, 1)
}
```

## كيف يكتشف "الحجب للأبد" تحديدًا؟

البروفايل يشغّل دورة **Garbage Collector** ليفحص قابلية الوصول: لو
goroutine `G` محجوبة على عنصر تزامن `P` (قناة، mutex...)، و`P` نفسه غير
قابل للوصول من أي goroutine **قابلة للتشغيل** (Runnable) أو من أي
goroutine تقدر تلك الأخيرة توقظها — فـ `P` لن يُحرَّك أبدًا، وبالتالي
`G` لن تستيقظ أبدًا. هذا بالضبط تعريف "المسرَّبة" هنا: ليست فقط
"محجوبة حاليًا"، بل **لا يوجد أي مسار ممكن** لتحريرها.

> 💡 لهذا السبب البروفايل **لا** يبلّغ عن goroutine تنتظر رد شبكة بطيء
> أو مهلة طويلة طبيعية — تلك محجوبة مؤقتًا فقط، وما زال هناك مسار
> (وصول الرد) قد يوقظها.

## الوصول عبر HTTP بخدمة قائمة

بنفس أسلوب أي بروفايل قياسي آخر (`heap`, `goroutine`...)، مجرّد استيراد
`net/http/pprof` بجانب [خادم HTTP](/learn/go/22-http-server) يعرّض
البروفايل تلقائيًا على مسار `/debug/pprof/goroutineleak`:

```go
import (
  "net/http"
  _ "net/http/pprof" // يسجّل مسارات /debug/pprof/* تلقائيًا
)

func main() {
  go http.ListenAndServe("localhost:6060", nil)
  // ... بقية الخادم
}
```

```bash
go tool pprof http://localhost:6060/debug/pprof/goroutineleak
```

`go tool pprof` يفتح واجهة تفاعلية تعرض المكدّس (stack trace) الكامل
لكل goroutine مسرَّبة — بالضبط أين تعلّقت بالكود، لا مجرّد عدد إجمالي.

## القيد المهمّ: قابلية الوصول عبر متغيّرات عامّة

لو عنصر التزامن (مثلًا القناة `ch`) يبقى قابلًا للوصول عبر **متغيّر
عامّ (global)** أو متغيّر محلّي بـ goroutine ما زالت قابلة للتشغيل، لن
يُكتشَف كتسريب — حتى لو لم يستخدمه أحد فعليًا بعد الآن. الأداة تعتمد
تحليل قابلية الوصول الحقيقي، لا تحليلًا لنيّة الكود.

> ⚠️ هذا يعني: البروفايل أداة تشخيص ممتازة، لكن غيابه من التقرير لا
> يعني "لا تسريبات إطلاقًا" — فقط "لا تسريبات قابلة للاكتشاف بتحليل
> قابلية الوصول."

## الفرق عن synctest

درس [اختبار الكود المتزامن](/learn/go/30-testing-concurrency) يغطّي
`testing/synctest` — أداة لجعل **اختبارات** الكود المتزامن حتمية
وسريعة أثناء التطوير. `goroutineleak` أداة مختلفة تمامًا بالغرض: تشخّص
**برنامجًا قيد التشغيل فعليًا** (تطوير أو حتى إنتاج) لإيجاد تسريبات لم
تُكتشف بالاختبار أصلًا.

## أخطاء شائعة

- تشغيل البروفايل مرّة واحدة فقط بعد الإقلاع مباشرة — التسريبات
  تتراكم مع الوقت؛ الأفضل مراقبته دوريًا على خدمة طويلة التشغيل أو عند
  ملاحظة نمو غير طبيعي بـ `runtime.NumGoroutine()`.
- الظن أن البروفايل يوقف أو "يصلح" الـ goroutine المسرَّبة — هو أداة
  **تشخيص وقراءة فقط**؛ إصلاح التسريب يبقى مسؤوليتك بالكود (مثلًا
  استخدام [`context`](/learn/go/26-context) لإلغاء العملية بدل تركها
  بلا نهاية).
- استيراد `net/http/pprof` بخادم إنتاج بدون تقييد الوصول لمسار
  `/debug/pprof/` — هذه المسارات تكشف تفاصيل داخلية حسّاسة، قيّدها
  بشبكة داخلية أو مصادقة منفصلة.
