بعد [درس 124: Vector Databases](/learn/ai-ml/124-vector-databases)، ندخل التطبيق العملي على **pgvector** — extension لـ PostgreSQL يضيف نوع `vector` وقدرات البحث.

## ما pgvector؟

```text
- امتداد لـ PostgreSQL.
- يضيف type جديد: vector(N).
- يضيف عوامل مسافة: <=>، <->، <#> .
- يدعم indexes: HNSW، IVFFlat.
- يبقى كل شيء في نفس قاعدة البيانات (علائقي + vector).
```

> مناسب حين تحتاج SQL + vectors + transactions في مكان واحد.

## التثبيت

```sql
-- على PostgreSQL 16+ مع pgvector 0.7+
CREATE EXTENSION IF NOT EXISTS vector;
```

## تعريف جدول بـ vector

```sql
CREATE TABLE chunks (
    id          BIGSERIAL PRIMARY KEY,
    doc_id      TEXT NOT NULL,
    chunk_index INTEGER NOT NULL,
    text        TEXT NOT NULL,
    embedding   vector(384) NOT NULL,    -- 384 بُعد لـ multilingual-e5-small
    source      TEXT,
    section     TEXT,
    language    TEXT,
    created_at  TIMESTAMPTZ DEFAULT now()
);
```

> **حجم العمود**: 384 floats × 4 bytes = ~1.5 KB per row (قبل index).

## عوامل المسافة

ثلاثة عوامل يقارن pgvector:

```text
<=> cosine distance = 1 - cosine_similarity
    (الأكثر شيوعًا في retrieval)
<-> L2 distance (Euclidean)
<#> inner product = -dot(q, d)
```

> **انتبه**: `<=>` يرجع **مسافة**، ليس تشابهًا. كلما **صغرت**، كلما زاد التشابه.

## INSERT مع embeddings

```python
import psycopg
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("intfloat/multilingual-e5-small")

chunks_data = [
    ("doc1", 0, "RAG retrieval-augmented generation."),
    ("doc1", 1, "Embeddings تحويل النصّ لمتجهات."),
    ("doc2", 0, "PostgreSQL قاعدة بيانات علائقية."),
]

texts = [c[2] for c in chunks_data]
# multilingual-e5 يتوقّع "passage: " كبادئة نصّية لكل مستند.
vecs = model.encode_document(
    [f"passage: {t}" for t in texts],
    normalize_embeddings=True,
)

with psycopg.connect("postgresql://user:pass@localhost/db") as conn:
    with conn.cursor() as cur:
        for (doc_id, idx, text), vec in zip(chunks_data, vecs):
            cur.execute(
                """INSERT INTO chunks (doc_id, chunk_index, text, embedding)
                   VALUES (%s, %s, %s, %s)""",
                (doc_id, idx, text, vec.tolist()),
            )
    conn.commit()
```

## البحث (exact NN)

```sql
-- cosine distance: أصغر = أفضل
SELECT id, text, embedding <=> %s::vector AS distance
FROM chunks
ORDER BY embedding <=> %s::vector
LIMIT 5;
```

```python
query = "كيف يجد النظام معلومات مشابهة؟"
q_vec = model.encode_query(f"query: {query}", normalize_embeddings=True)

with psycopg.connect("postgresql://user:pass@localhost/db") as conn:
    with conn.cursor() as cur:
        cur.execute(
            """SELECT id, text, embedding <=> %s::vector AS distance
               FROM chunks
               ORDER BY embedding <=> %s::vector
               LIMIT 5""",
            (q_vec.tolist(), q_vec.tolist()),
        )
        for row in cur.fetchall():
            print(f"{row[2]:.3f}  {row[1]}")
```

```text
⚠️ بدون index = exact NN (بطيء عند ملايين).
```

## HNSW Index

لـ ANN (أسرع بكثير):

```sql
CREATE INDEX ON chunks
USING hnsw (embedding vector_cosine_ops);
```

**opclass يحدّد metric الـ index**:

```text
vector_cosine_ops      لـ <=> (cosine distance)
vector_l2_ops          لـ <-> (Euclidean)
vector_ip_ops          لـ <#> (inner product)
```

> **قاعدة صارمة**: opclass يجب أن يطابق الـ operator المستخدم في الـ query. عند عدم التطابق:
>
> - الـ operator نفسه يحسب المسافة بالـ formula الأصلية في كل مرة، فلا يحصل "خطأ حسابي" في النتيجة.
> - لكن الـ index المصمَّم لهذا الـ opclass بالذات لا يمكنه خدمة الـ operator هذا (opclass mismatch).
> - ما يفعله PostgreSQL بالضبط يعتمد على الـ planner والـ indexes المتوفّرة: قد يلجأ إلى exact scan فوق الجدول، أو distance scan من دون الـ ANN index، أو مسار آخر. لا يوجد ضمان سلوك واحد ثابت.
>
> الخلاصة العملية: تأكّد من تطابق opclass مع operator لتحصل على ANN الفعلي، وإلا فالـ index لا يخدم هذا الـ query.

### معاملات HNSW

```sql
CREATE INDEX ON chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

```text
m:
  - عدد الـ edges لكل node.
  - pgvector default = 16 (هذه قيمة افتراضية pgvector فقط؛
    القيم في إصدارات أخرى من HNSW قد تختلف).
  - قيمة أكبر = graph أكثف = recall أفضل، ذاكرة أكبر.

ef_construction:
  - candidate list عند البناء.
  - pgvector default = 64 (نفس الملاحظة — خاص بـ pgvector).
  - أكبر = index أبطأ بناءً لكن recall أعلى.
```

### ef_search

```sql
-- ef_search يضبط وقت الاستعلام (session-level)
SET hnsw.ef_search = 100;
```

```text
- لـ pgvector قيمة افتراضية لـ ef_search (راجع وثائق إصدارك).
- رفع ef_search = زيادة breadth للبحث داخل الـ graph = recall أعلى
  عادةً، بـ latency أعلى أيضًا.
- لا توجد "نطاق معقول عالمي" صالح لكل البيانات؛ اختبر recall@K
  وlatency على بياناتك الفعلية عند اختيار قيمة.
```

## IVFFlat Index

بديل أخفّ:

```sql
CREATE INDEX ON chunks
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

```text
lists:
  - عدد الخلايا (k-means clusters).
  - لا توجد صيغة عالمية صارمة لـ lists مقابل حجم الـ corpus
    (وتتغيّر بحسب بُعد الـ embedding، توزيع البيانات، والـ recall المطلوب).
  - قبل اختيار قيمة: راجع وثائق pgvector الحالية لإصدارك، ثم
    قِس recall@K ولاتنسي على بياناتك وعدّل lists بناءً على النتيجة.
  - لا تعتمد على قاعدة إبهام واحدة تخصّ إصدارًا قديمًا.
```

```text
✅ IVFFlat:
  - أبسط، أقلّ ذاكرة من HNSW.
  - يحتاج تدريب k-means أولًا (مرّة واحدة عند BUILD).

⚠️ IVFFlat:
  - أقلّ recall من HNSW عادةً.
  - حسّاس لاختيار lists.
  - قد يكون بطيئًا على corpus صغير جدًا لأن k-means
    يتطلّب بيانات كافية لإنشاء clusters ذات معنى.
```

## HNSW مقابل IVFFlat في pgvector

```text
HNSW:
  ✅ recall@10 عالي.
  ✅ سريع في الاستعلام.
  ❌ rebuild بطيء، ذاكرة أكبر.

IVFFlat:
  ✅ أبسط.
  ✅ أقلّ ذاكرة.
  ❌ أقلّ recall عادةً.
  ❌ يحتاج تدريب (k-means).
  ❌ حسّاس للقيم المتطرّفة (outliers).
```

> **لا توجد قاعدة عامة.** جرّب على بياناتك وقِس recall@10.

## Filtering + Vector Search

```sql
-- فلترة على metadata + vector
SELECT id, text, embedding <=> %s::vector AS distance
FROM chunks
WHERE language = 'ar'                -- metadata filter
ORDER BY embedding <=> %s::vector
LIMIT 5;
```

```text
⚠️ الفلترة على metadata تعمل لكن قد تُضعف recall
   إذا فلترت مبكرًا قبل حساب التشابه.
```

للفلترة السريعة على metadata:


## اختيار Opclass

```text
- embeddings من نموذج retrieval مع cosine:
  CREATE INDEX ... USING hnsw (embedding vector_cosine_ops);
  → استخدم <=> في الاستعلام.

- embeddings normalized:
  cosine = dot product.
  → يمكنك تجربة vector_ip_ops مع <#> إذا أردت.

- embeddings من نموذج Euclidean:
  CREATE INDEX ... USING hnsw (embedding vector_l2_ops);
  → استخدم <-> في الاستعلام.
```

> **مهم**: opclass والـ operator يجب أن يتطابقا للاستفادة من الـ index. عند عدم التطابق:
>
> - حساب المسافة نفسه يبقى صحيحًا (الـ operator يحسب بالـ formula الأصلية في كل مرة).
> - الـ index المصمَّم لهذا الـ opclass بالذات لا يمكنه خدمة الـ operator هذا، فلا يُستخدم لإعطاء ترتيب الـ ANN.
> - PostgreSQL عندها يختار خطة أخرى بحسب الـ schema والـ indexes والـ filters وقرارات الـ planner: قد يلجأ إلى exact scan فوق الجدول، أو distance scan من دون الـ ANN index، أو مسار آخر. لا يوجد ضمان سلوك واحد محدّد.

```sql
-- يجب أن تطابق بُعد النموذج
CREATE TABLE chunks (

CREATE TABLE chunks_other (

```

```text
خلط أبعاد في عمود واحد = خطأ.
```

## أخطاء شائعة

- **"استخدم HNSW دائمًا"**: يعتمد. IVFFlat أبسط وأخفّ، قد يكفي.
- **"opclass لا يهمّ"**: لا. عدم تطابق opclass مع operator يعني أن PostgreSQL لا يستطيع استخدام الـ ANN index للترتيب، فيختار خطة أخرى (مثل exact scan أو distance scan) بحسب الـ schema والـ indexes والـ filters. النتيجة تبقى صحيحة حسابيًا، لكنك تفقد تسريع الـ ANN.
- **"ef_search = 40 كافٍ"**: يعتمد. قِس recall@10.
- **"lists = 100 لـ 10 ملايين"**: لا. lists معامل tuning يعتمد على حجم الـ corpus وحجم cluster — اختبر على بياناتك.
- **"ANN يضمن recall=1"**: لا. ANN ≈ nearest neighbor. قِس recall@10.

## معاملات الـ Index ومتى تُعيد البناء

```text
- dataset تغيّر كثيرًا (insertions بالجملة):
  HNSW أبطأ في الـ insertion من IVFFlat.
  قد تحتاج rebuild دوري.

- dataset مستقر:
  HNSW أكثر ملاءمة.
```
