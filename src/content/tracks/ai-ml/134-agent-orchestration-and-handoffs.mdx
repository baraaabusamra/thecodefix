## ما Multi-Agent؟

```text
single agent:
  - LLM واحد + tools + state.
  - كل الأعباء على عاتقه.

multi-agent:
  - عدّة agents متخصّصون.
  - واحد يوجّه، آخرون ينفّذون.
  - فصل المسؤوليات.
```

## لماذا Multi-Agent؟

```text
✅ تخصّص:
  - agent لكل مجال (math، search، support، ...).
  - instructions قصيرة ومركّزة.
  - أداء أفضل من agent عام.

✅ فصل:
  - tools لكل agent.
  - error handling أسهل.
  - debugging أبسط.

✅ cost:
  - agent صغير = model أصغر = أرخص.
  - agent متخصّص = prompt أقصر.
```

## أنماط Multi-Agent

### 1. Triage (الموجّه)

```text
- agent رئيسي (triage) يصنّف الطلب.
- يحوّل (handoff) لـ agent متخصّص.
- agent المتخصّص ينفّذ ويعود.
```

```python
import os
from agents import Agent, Runner

# الـ model من environment — اختيار provider/model قرار setup،
# لا حقيقة من منهاج ثابت.
DEFAULT_MODEL = os.environ["OPENAI_MODEL"]  # مثلاً: "gpt-4o-mini"

# متخصّصون
math_agent = Agent(
    name="MathAgent",
    instructions="أنت متخصّص في الرياضيات.",
    tools=[calculator],
    model=DEFAULT_MODEL,
)

support_agent = Agent(
    name="SupportAgent",
    instructions="أنت متخصّص في دعم العملاء.",
    tools=[search_docs, escalate_ticket],
    model=DEFAULT_MODEL,
)

# triage
triage = Agent(
    name="Triage",
    instructions="""صنّف الطلب ثم وجّهه للـ agent المناسب.
- رياضيات → MathAgent.
- دعم عملاء → SupportAgent.
- غير ذلك → أجب أنت أو ارفض.""",
    model=DEFAULT_MODEL,
    handoffs=[math_agent, support_agent],
)

result = Runner.run_sync(triage, "احسب 15 * 23.", max_turns=10)
print(result.final_output)
```

```text
- triage يستقبل الطلب.
- يقرّر: math → MathAgent.
- MathAgent ينفّذ ويعود.
```

### 2. Supervisor (المشرف)

```text
- supervisor agent يدير عدّة workers.
- يوزّع المهام.
- يجمع النتائج.
- workers لا يتواصلون مباشرة.
```

```python
# مثال supervisor pattern (يدوي)
def supervisor_workflow(user_request: str) -> str:
    plan = supervisor_llm.create_plan(user_request)
    # → ["research", "summarize"]

    research_results = research_agent.run(plan[0])
    summary = summarize_agent.run(plan[1], context=research_results)

    return supervisor_llm.synthesize(research_results, summary)
```

### 3. Pipeline (خط أنابيب)

```text
- agent 1 → agent 2 → agent 3.
- كل واحد يأخذ output السابق.
- deterministic بشكل عام من حيث الـ graph (نفس الخطوات بنفس الترتيب)، لكن مخرجات LLM تظل statistical.
```

```python
def pipeline_research(topic: str) -> str:
    outline = outline_agent.run(f"اكتب outline عن: {topic}")
    content = content_agent.run(f"اشرح: {outline}")
    edited = editor_agent.run(f"حرّر: {content}")
    return edited
```

### 4. Collaborative (التعاون)

```text
- agents يتواصلون مع بعضهم.
- peer-to-peer.
- معقّد، debugging صعب.
```

> هذا النمط أقلّ شيوعًا في production لأنه صعب التشخيص.

## Handoffs: التفصيل

في OpenAI Agents SDK:

```python
# handoff ببساطة = إضافة agent في handoffs
specialist = Agent(name="Specialist", ...)
triage = Agent(
    name="Triage",
    handoffs=[specialist],
)
```

```text
ما يحدث:
  1. triage يقرّر: "هذه المهمة لـ specialist".
  2. SDK ينقل active control إلى specialist داخل run واحد.
  3. specialist ينفّذ (مع tools + state).
  4. عند انتهاء specialist، ينتهي run الـ agent
     (الناتج النهائي = final_output للـ specialist).
  5. control لا "يعود" آليًا إلى triage بعد ذلك داخل
     الـ run نفسه؛ إذا أردت supervisor pattern (توجيه
     من triage + جمع نتائج)، استخدم Agent.as_tool()
     بدل handoffs — موضّح في قسم "Agent as Tool" تحت.

handoff هو tool ضمني:
  - specialist name = tool name.
  - input description = tool description.
  - LLM يستدعيه كما يستدعي function، لكن الفرق عن
    tool حقيقي: tool يُعيد قيمة إلى الـ caller، أمّا
    handoff فيحوّل الـ active agent داخل الـ run.
```

## Agent as Tool (Supervisor Pattern)

عندما تريد أن يبقى manager واحد في المقدمة ويستدعي
specialists كأدوات ويجمع النتائج — استخدم
`Agent.as_tool(...)`. هذه الـ pattern مناسبة لـ
**Manager/Supervisor** حيث يكون الـ manager هو
الـ active agent طول الوقت والـ specialists ينفّذون
sub-tasks ثم يُعيدون نتائجهم للمدير.

```python
from agents import Agent, Runner

# متخصّص Retrieval: يبحث فقط، يُعيد chunks كقائمة.
retrieval_agent = Agent(
    name="Retriever",
    instructions="استرجع المستندات ذات الصلة. لا تولّد إجابة. أعد مقاطعًا مرقّمة.",
    tools=[vector_search, bm25_search],
    model=DEFAULT_MODEL,
    # مهم لـ as_tool: output_type يجب أن يكون نوعًا منظّمًا
    # أو string واضح حتى يتعامل معه الـ manager بسهولة.
)

# متخصّص Writer: يكتُب من مستندات مُمرَّرة له.
writer_agent = Agent(
    name="Writer",
    instructions="اكتب إجابة بالعربية بناءً على المستندات المُمرَّرة لك. استشهد بالأرقام.",
    model=DEFAULT_MODEL,
)

supervisor = Agent(
    name="RAGSupervisor",
    instructions=(
        "1) استدعِ retrieval_agent كـ tool للحصول على المستندات. "
        "2) استدعِ writer_agent كـ tool للحصول على إجابة منظّمة. "
        "3) لخّص للمستخدم."
    ),
    tools=[
        retrieval_agent.as_tool(
            tool_name="retrieve_docs",
            tool_description="استرجع المستندات ذات الصلة بسؤال. أعد مقاطعًا مرقّمة.",
        ),
        writer_agent.as_tool(
            tool_name="write_answer",
            tool_description="اِكتب إجابة بالعربية من المستندات المرفقة. استخدم الـ citations.",
        ),
    ],
    model=DEFAULT_MODEL,
)

result = Runner.run_sync(supervisor, "ما الفرق بين HNSW و IVFFlat؟")
# supervisor يبقى الـ active agent طوال الـ run، ويستدعي
# specialists كأدوات، ثم يجمع النتيجة النهائية.
```

```text
الفرق عن handoffs:
- handoff: ينقل control للـ specialist داخل run واحد.
  مناسب إذا أردت للـ specialist أن يقدّم الإجابة النهائية.
- as_tool: المدير يبقى في المقدّمة ويستدعي specialists كأدوات
  تأخذ قيمًا وترجعها. مناسب لـ manager/supervisor pattern.
```

## Multi-Agent RAG

```python
# نفس الـ retrieval_agent و writer_agent أعلاه، والمُستخدَمان
# عبر as_tool (الموصى به) — استخدم as_tool بدل handoffs
# لأن مدير RAG يبقى في المقدّمة ويجمع النتائج.

retrieval_agent = Agent(
    name="Retriever",
    instructions="استرجع المستندات ذات الصلة. لا تولّد إجابة.",
    tools=[vector_search, bm25_search],
    model=DEFAULT_MODEL,
)

writer_agent = Agent(
    name="Writer",
    instructions="اكتب إجابة بالعربية بناءً على المستندات المعطاة. استشهد بالأرقام.",
    model=DEFAULT_MODEL,
)

supervisor = Agent(
    name="RAGSupervisor",
    instructions="1) استدعِ retrieve_docs. 2) استدعِ write_answer مع المستندات. 3) لخّص.",
    tools=[
        retrieval_agent.as_tool(
            tool_name="retrieve_docs",
            tool_description="استرجع المستندات ذات الصلة بسؤال.",
        ),
        writer_agent.as_tool(
            tool_name="write_answer",
            tool_description="اِكتب إجابة بالعربية من المستندات المُمرَّرة.",
        ),
    ],
    model=DEFAULT_MODEL,
)

result = Runner.run_sync(supervisor, "ما الفرق بين HNSW و IVFFlat؟")
```

## حدود Multi-Agent

```text
❌ لا تستخدم multi-agent حين:
  - المهمة بسيطة (agent واحد كافٍ).
  - latency < 1s (multi-agent أبطأ).
  - ميزانية per-request منخفضة جدًا (multi-agent يكلّف أكثر عادةً — يعتمد على provider/model الفعلي).
  - debugging سهل مطلوب.

⚠️ تحديات:
  - context متعدّد = صعب التشخيص.
  - كل agent له tokens = cost عالي.
  - error propagation: فشل واحد = فشل الكل.
```

## Cost Optimization

```text
✅ لتوفير cost:
  - agents متخصّصون يستخدمون provider/model أرخص متاح
    (الاسم قرار إعداد — اختبر trade-off quality vs cost).
  - routing/triage يستخدم provider/model أقوى فقط للقرارات الصعبة.
  - cap max_turns لكل agent.
  - log + راقب cost per agent على usage الفعلي.
```

## Tracing Multi-Agent

```python
result = Runner.run_sync(supervisor, "...", max_turns=20)

# استكشف الـ turns
for item in result.new_items:
    if hasattr(item, "agent"):
        print(f"[{item.agent}] {item.type}: {item}")
```

```text
Tracing ضروري لـ:
  - من اتخذ القرار؟
  - كم turn لكل agent؟
  - ما الـ tool calls؟
  - ما الـ tokens المستهلكة؟
```

## Failure Modes

```text
1. Handoff loop:
   - agent A يحوّل لـ B، B يحوّل لـ A.

2. No handoff:
   - triage لا يعرف أي agent يختار.

3. State contamination:
   - state agent A يصل لـ B بدون قصد.

4. Cost explosion:
   - N agents × M turns × tokens per turn × سعر provider/model.

5. Lost context:
   - بعد 3 handoffs، الـ original task يضيع.
```

## Best Practices

```text
1. max_turns لكل agent:
   - حتى لا يدخل agent في loop.

2. instructions واضحة:
   - "لا تولّد إجابة، فقط استرجع."
   - "أنت متخصّص في X فقط."

3. tools موثّقة:
   - description واضح.
   - errors واضحة.

4. tracing:
   - شغّل OPENAI_AGENTS_TRACE=1.
   - راجع كل run.

5. eval set:
   - اختبارات ثابتة لكل agent.

6. fallback:
   - إذا فشل كل agents → fallback LLM.
```

## مقارنة Multi-Agent و Single Agent

```text
single agent:
  ✅ أبسط.
  ✅ cost أقلّ.
  ❌ قد يخفّق في تخصّصات.
  ❌ instructions طويلة (generalist).

multi-agent:
  ✅ تخصّص.
  ✅ cost يمكن تحسينه (small models per agent).
  ❌ debugging أصعب.
  ❌ context management معقّد.
```

## متى تختار كل نمط

```text
triage:
  - طلبات متعدّدة الأنواع.
  - كل نوع له agent متخصّص.
  - مثال: customer service router.

supervisor:
  - مهمة معقّدة تتطلّب planning.
  - workers ينفّذون subtasks.
  - مثال: research assistant.

pipeline:
  - خطوات ثابتة ومعروفة.
  - كل خطوة لها output واضح.
  - مثال: drafting → editing → review.

collaborative:
  - peer discussion مطلوب.
  - مثال: debate / consensus.
  - ⚠️ debugging صعب.
```

## أخطاء شائعة

- **"multi-agent دائمًا أفضل"**: لا. single agent أرخص وأبسط لكثير من المهام.
- **"handoff = حلقة لا نهائية"**: لا. مع max_turns صريح.
- **"كل agents تستخدم نفس model"**: لا. متخصّصون يستخدمون model أصغر.
- **"لا tracing في multi-agent"**: خطر. مستحيل التشخيص.
- **"handoff ينقل كل الـ state"**: يعتمد. SDK يديرها، لكن راجع.

## Production Tips

```text
- ابدأ single agent.
- إذا رأيت bottleneck (الـ model يخفّق في تخصّص) → قسّمه.
- إذا رأيت cost مرتفع → أضف triage و workers أرخص.
- راقب:
  - cost per request.
  - latency per request.
  - success rate per agent.
- اختبر مع eval set ثابت.
```
