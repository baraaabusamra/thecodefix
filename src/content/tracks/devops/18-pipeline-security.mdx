## أهمية أمن الـ CI/CD

خط CI/CD هو بوابة الكود إلى الإنتاج. أي ثغرة فيه تعرض كل شيء للخطر.

## إدارة الأسرار (Secrets)

```yaml
# استخدم GitHub Secrets، لا تضع الأسرار في الكود
- name: Deploy
  env:
    API_KEY: ${{ secrets.API_KEY }}
    DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
  run: ./deploy.sh
```

## فحص الأسرار المكشوفة

```yaml
- name: Secret Scan
  uses: trufflesecurity/trufflehog@main
  with:
    extra_args: --results=verified,unknown
```

## التوقيع على الـ Commits

```bash
# تكوين GPG
git config --global user.signingkey KEY_ID
git config --global commit.gpgsign true

# التوقيع على commit
git commit -S -m "feat: رسالة commit موقعة"
```

## تأمين الـ CI Pipeline

```yaml
# منع تشغيل pipeline على Forks
on:
  pull_request:
    branches: [main]

# تقييد صلاحيات الـ Token
permissions:
  contents: read
  issues: write
```

> ⚠️ لا تمنح `GITHUB_TOKEN` صلاحيات أكبر من اللازم. طبق مبدأ Least Privilege.

## فحص التبعيات (Dependency Scanning)

```yaml
- name: Dependabot Analysis
  run: |
    npm audit --audit-level=high
    # أو
    dotnet list package --vulnerable
```

## قراءة تنبيهات Dependabot مباشرة من الـ workflow

الفحص أعلاه (`npm audit` أو ما يعادله) يفحص التبعيات من جديد في كل تشغيلة، لكنه لا يعرف شيئاً عن تنبيهات Dependabot الموجودة أصلاً في تبويب Security بالمستودع. للوصول لتلك التنبيهات نفسها عبر الـ API، كان `GITHUB_TOKEN` الافتراضي لا يكفي — الحل السابق كان توليد Personal Access Token بصلاحية `repo` أو `security_events` كاملة وتخزينه كسر، وهو تجاوز واضح لمبدأ Least Privilege المذكور أعلاه لمجرد قراءة تنبيهات.

منذ سبتمبر 2026، أضافت GitHub صلاحية جديدة مخصصة لـ `GITHUB_TOKEN` تحديداً لهذا الغرض:

```yaml
permissions:
  contents: read
  vulnerability-alerts: read   # صلاحية قراءة فقط، جديدة في سبتمبر 2026

jobs:
  check-alerts:
    runs-on: ubuntu-latest
    steps:
      - name: عرض تنبيهات Dependabot المفتوحة
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh api repos/${{ github.repository }}/dependabot/alerts \
            --jq '.[] | select(.state == "open") | .security_advisory.summary'
```

`vulnerability-alerts` تقبل قيمتين فقط: `read` أو `none` — لا توجد قيمة كتابة، لأن الغرض الوحيد منها هو منح `GITHUB_TOKEN` وصولاً للقراءة فقط بدل الاضطرار لتوكن شخصي أوسع صلاحية.

> 💡 هذه الصلاحية بديل لـ Personal Access Token واسع الصلاحية عندما يحتاج الـ workflow فقط قراءة تنبيهات Dependabot الموجودة (مثلاً لإيقاف النشر إن وُجد تنبيه حرج مفتوح) — لا لتشغيل فحص تبعيات جديد من الصفر، فهذا يبقى دور `npm audit` وأدواته المشابهة.
