## مشكلة تكرار YAML

بعد سلسلة الدروس السابقة، غالباً صار عندك أكثر من workflow يكرر نفس الخطوات — تثبيت التبعيات، تشغيل الاختبارات، تسجيل الدخول لسجل الحاويات. GitHub Actions يوفر أداتين لكسر هذا التكرار، وكل واحدة تحل مستوى مختلف من المشكلة: **Composite Actions** لتجميع خطوات متكررة داخل job واحد، و**Reusable Workflows** لتجميع jobs كاملة يُعاد استخدامها عبر workflows مختلفة.

## Composite Actions: تجميع خطوات متكررة

Composite Action تحزم عدة خطوات (steps) في "action" واحد يُستدعى كخطوة واحدة من أي workflow.

```yaml
# .github/actions/setup-project/action.yml
name: "Setup Project"
description: "تثبيت التبعيات وإعداد بيئة Node.js"
inputs:
  node-version:
    description: "إصدار Node.js"
    required: false
    default: "20"
runs:
  using: "composite"
  steps:
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: "npm"
    - run: npm ci
      shell: bash
```

استخدامها من أي workflow في نفس المستودع:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/setup-project
        with:
          node-version: "22"
      - run: npm test
```

- كل خطوة داخل composite action تحتاج `shell` صراحة (عادة `bash`)
- تُستدعى بـ `uses: ./.github/actions/<اسم-المجلد>` من نفس المستودع، أو `uses: owner/repo@ref` من مستودع منفصل
- في سجل التشغيل، تظهر كخطوة واحدة مجمّعة — الخطوات الداخلية لا تُعرض كل واحدة على حدة في الملخص الرئيسي

## Reusable Workflows: تجميع Jobs كاملة

عندما يكون التكرار على مستوى workflow كامل (بناء + اختبار + نشر بعدة jobs)، لا تكفي composite action لأنها تعمل داخل job واحد فقط. الحل هو **reusable workflow**: ملف workflow عادي يُفعَّل بـ `workflow_call` بدل (أو بجانب) `push`/`pull_request`.

```yaml
# .github/workflows/reusable-test.yml
on:
  workflow_call:
    inputs:
      node-version:
        type: string
        default: "20"
    secrets:
      npm-token:
        required: false

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
      - run: npm ci && npm test
        env:
          NODE_AUTH_TOKEN: ${{ secrets.npm-token }}
```

استدعاؤها من workflow آخر يكون على مستوى الـ job نفسه، بـ `uses` بدل `runs-on`:

```yaml
# .github/workflows/ci.yml
on: push

jobs:
  call-tests:
    uses: ./.github/workflows/reusable-test.yml
    with:
      node-version: "22"
    secrets:
      npm-token: ${{ secrets.NPM_TOKEN }}
    # أو ببساطة: secrets: inherit
```

- `{ref}` في الاستدعاء عبر مستودعات مختلفة يقبل SHA أو tag أو اسم فرع
- `secrets: inherit` يمرر كل أسرار الـ caller تلقائياً بدل تعدادها واحداً واحداً
- يمكن لـ reusable workflow أن يُرجع outputs عبر `outputs` على مستوى `workflow_call` تُقرأ في الـ caller بـ `needs.<job>.outputs.<name>`

## الفرق بينهما

| المعيار | Composite Action | Reusable Workflow |
|---------|-------------------|---------------------|
| ما يحزّمه | خطوات (steps) | jobs كاملة |
| نقطة الاستدعاء | داخل `steps` في job موجود | مستوى `jobs` نفسه (`uses` بدل `runs-on`) |
| عدة jobs بأنواع runners مختلفة | لا يدعم | يدعم |
| ظهوره في سجل التشغيل | خطوة واحدة مجمّعة | كل job وخطواته تظهر منفصلة |
| الأنسب لـ | خطوات تحضيرية متكررة (تثبيت، تسجيل دخول) | خط أنابيب كامل متكرر بين عدة مشاريع |

> ⚠️ إذا احتجت فقط تجميع بضع خطوات داخل نفس الـ job، composite action أبسط وكافية. لا تلجأ لـ reusable workflow إلا إذا كان التكرار فعلاً على مستوى jobs متعددة أو runners مختلفة — التعقيد الإضافي لا يستحق العناء لحالة بسيطة.

## الإشارة لنفس المستودع بصيغة `$/`

كل الأمثلة أعلاه تستدعي composite action أو reusable workflow من نفس المستودع بصيغة `uses: ./.github/...`. هذا يعمل، لكنه يعتمد ضمنياً على وجود checkout سابق في نفس الـ job (composite action محلي بلا checkout لا يجد الملف أصلاً). GitHub أضاف صيغة جديدة `$/` تحل هذا بدون الحاجة لـ checkout إطلاقاً: قيمة `uses` التي تبدأ بـ `$/` تُحل تلقائياً لمستودع الـ workflow نفسه، عند نفس الـ commit الذي يعمل عليه التشغيل الحالي بالضبط.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: $/.github/actions/setup-project
        with:
          node-version: "22"
      - run: npm test
```

- تعمل `$/` في كل مكان تعمل فيه `./` النسبية لمساحة العمل: خطوات الـ job، خطوات composite action، التركيب المتداخل (nested composition)، واستدعاء reusable workflow
- الفرق الجوهري عن `./`: لا حاجة لخطوة `actions/checkout` مسبقاً لأن `$/` تُحل من جهة GitHub مباشرة، لا من ملفات مستنسخة على القرص
- عند استدعاء الـ caller نفسه بواسطة SHA كامل مثبّت (commit pinning)، أي مرجع `$/` داخلي يتبع تلقائياً نفس الـ SHA — فتبقى الإشارات الداخلية متزامنة مع الاستدعاء الخارجي دون أي إعداد إضافي
- تتطلب self-hosted runners إصداراً `2.336.0` أو أحدث لدعم `$/`؛ GitHub-hosted runners تدعمها تلقائياً

> 💡 صيغة `$/` لا تلغي `./` — الأخيرة تبقى مفيدة إذا كنت تحتاج فعلياً checkout لأسباب أخرى في نفس الخطوة. لكن لتقليل عدد الخطوات وتجنّب الاعتماد على checkout فقط من أجل استدعاء action محلي، `$/` هي الخيار الأحدث والأبسط.

## معرفة الـ reusable workflow لمصدره الخاص: خصائص job.*

سياق `github` (`github.workflow_ref`, `github.workflow_sha`) يشير دائماً لملف الـ workflow الذي استقبل الحدث الأصلي — أي workflow الـ **caller**، حتى داخل job معرَّف فعلياً بملف reusable workflow منفصل. هذا كان يمثل مشكلة حقيقية: لو احتاج reusable workflow قراءة سكربت أو ملف موجود بجانبه في مستودعه الخاص (لا في مستودع الـ caller)، لم يكن هناك سياق مدمج يخبره بمرجعه أو الـ commit الخاص به هو نفسه — والحل الشائع سابقاً كان actions خارجية طرف ثالث تستنتج ذلك يدوياً.

GitHub أضاف سياق `job` بأربع خصائص جديدة تحل هذا تحديداً، وتصف ملف الـ workflow الذي **يُعرِّف الـ job الحالي فعلياً** — لا الـ caller دائماً:

```yaml
# .github/workflows/reusable-build.yml
on:
  workflow_call:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      # يسحب مستودع الـ reusable workflow نفسه عند نفس الـ commit الذي استُدعي به،
      # لا مستودع الـ caller الذي استدعى هذا الـ workflow
      - uses: actions/checkout@v7
        with:
          repository: ${{ job.workflow_repository }}
          ref: ${{ job.workflow_sha }}
      - run: cat ./scripts/build.sh   # سكربت موجود بجانب هذا الملف نفسه، لا بجانب الـ caller
```

| الخاصية | ماذا تصف |
|---------|-----------|
| `job.workflow_ref` | مرجع (فرع/tag) ملف الـ workflow المُعرِّف للـ job الحالي |
| `job.workflow_sha` | commit SHA لذلك الملف |
| `job.workflow_repository` | `owner/repo` الذي يحتوي ملف الـ workflow |
| `job.workflow_file_path` | مسار ملف الـ workflow نسبة لجذر ذلك المستودع |

لجوب معرَّف مباشرة في نفس workflow الـ caller (بلا `workflow_call`)، تتطابق قيم `job.*` مع `github.workflow_ref` / `github.workflow_sha` تماماً — الفرق يظهر فقط داخل job قادم من reusable workflow مستدعى.

> ⚠️ هذه الخصائص متاحة على GitHub.com فقط حتى الآن، وغير مدعومة على GitHub Enterprise Server — تحقق من التوفر قبل الاعتماد عليها إن كان مشروعك يشغّل نسخة ذاتية الاستضافة.
