## لماذا هذا الدرس؟

مشكلة مألوفة لكل من يعمل بفروع طويلة: تبني ميزة كبيرة، فتتراكم عشرات الـ commits في فرع واحد، ويفتح Pull Request ضخم يصعب على أي مراجع قراءته دفعة واحدة. الحل التقليدي كان يدويًا: تفتح فرعًا فوق فرع (`git switch -c part-2 part-1`)، وتفتح PR يستهدف `part-1` بدل `main`، وتتابع يدويًا أي فرع يعتمد على أي فرع.

في 30 يوليو 2026 أطلق GitHub **Stacked Pull Requests** كميزة رسمية في **معاينة عامة (Public Preview)** — نفس الفكرة، لكن GitHub يتتبّع السلسلة بنفسه بدل أن تتذكّرها أنت.

> ⚠️ الميزة لا تزال Public Preview وقت كتابة هذا الدرس — التفاصيل هنا قد تتغيّر مع خروجها من المعاينة.

## الفكرة: سلسلة PRs، كل واحد فوق سابقه

الكومة (Stack) هي عدّة Pull Requests بنفس المستودع، بالترتيب:

- أول PR يستهدف الفرع الافتراضي (`main` غالبًا) — تمامًا كأي PR عادي (راجع [درس GitHub وطلبات السحب](/learn/git/21-github-pull-requests)).
- كل PR بعده يستهدف **فرع الـ PR الذي قبله**، لا `main` مباشرة.

```bash
git switch -c auth-part1 main
# ... commits الجزء الأول ...
git push -u origin auth-part1
# افتح PR: auth-part1 → main

git switch -c auth-part2 auth-part1
# ... commits الجزء الثاني، يعتمد على الأول ...
git push -u origin auth-part2
# افتح PR: auth-part2 → auth-part1
```

عند فتح PR الثاني من واجهة GitHub، تظهر خيار "إضافة إلى كومة" (Add to stack) لأن GitHub يلاحظ أن الفرع الأساس (`auth-part1`) نفسه له PR مفتوح — فيربط بينهما تلقائيًا ويعرضهما كوحدة واحدة في واجهة الـ PR.

## ماذا يحدث عند الدمج

هنا الفرق الحقيقي عن سلسلة فروع يدوية: لما تدمج PR معيّن في الكومة، **كل الـ PRs غير المدموجة تحته تُدمج معه بعملية واحدة**، مرتّبة من الأسفل للأعلى في التاريخ الناتج. أي PRs تبقى فوقه مفتوحة تُعاد كتابتها (rebase) تلقائيًا لتستهدف قاعدة الكومة مباشرة — فتنزل خطوة واحدة في السلسلة بدل أن تُترك تشير لفرع أُغلق.

يعني تقدر تدمج جزءًا من الميزة (الطبقات السفلى الجاهزة) بينما الطبقات العليا لا تزال قيد المراجعة، دون أن تنكسر أي علاقة بين الفروع.

## شروط الدمج

قبل أن يقبل GitHub دمج أي PR ضمن كومة:

- كل الـ PRs الأسفل منه يجب أن تكون **موافَق عليها (Approved)** وفحوصاتها (CI) ناجحة.
- تاريخ الكومة يجب أن يبقى **خطّيًا (linear)** — لا merge commits داخلها.
- الـ PR الحالي يجب أن يحقّق أي قاعدة حماية فرع (branch protection) مطبّقة على قاعدة الكومة.

> 💡 استخدم [rebase التفاعلي](/learn/git/29-interactive-rebase) لتنظيف كل طبقة قبل فتح الـ PR الخاص بها — كومة من PRs نظيفة كل واحد بمقصده الواحد هي كل الفائدة من الميزة.

## قيود المعاينة الحالية

- **الدمج التلقائي (Auto-merge) غير مدعوم** لطلبات السحب المكدّسة حاليًا.
- دعم **قائمة الدمج (Merge Queue)** للكومات لا يزال يُفعَّل تدريجيًا على المستودعات — تأكّد أنه فعّال على مستودعك قبل الاعتماد عليه مع كومة تحتاج قائمة دمج.

## أداة سطر أوامر اختيارية: gh stack

لمن يفضّل الطرفية على الواجهة، توفّر GitHub امتدادًا رسميًا لأداة `gh` باسم `gh-stack` بثلاثة أوامر أساسية:

```bash
gh stack init      # يبدأ كومة جديدة من الفرع الحالي
gh stack add       # يضيف طبقة جديدة فوق الكومة الحالية
gh stack checkout  # يتنقّل بين طبقات الكومة برقمها
```

هذا امتداد منفصل (يحتاج `gh` إصدار 2.0 فأعلى)، وهو أيضًا Public Preview — تفاصيل خياراته الدقيقة قابلة للتغيير، فراجع توثيق GitHub الرسمي قبل الاعتماد عليه في سير عمل فريقك.

## متى تستخدمها؟

- ميزة كبيرة تتكوّن منطقيًا من عدّة خطوات مستقلّة قابلة للمراجعة كل واحدة على حدة.
- فريق يريد مراجعات أسرع وأدق بدل PR واحد بمئات الأسطر.

لا تستخدمها لمجرّد تقسيم عمل غير مترابط فعليًا — لو الأجزاء لا تعتمد على بعضها منطقيًا، افتحها كـ PRs منفصلة تستهدف `main` مباشرة، أبسط للمراجعة من كومة غير ضرورية.
